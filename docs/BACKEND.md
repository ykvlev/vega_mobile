# VEGA — backend и данные

Актуально на 26 октября 2026. Бизнес-решения — [DECISIONS.md](DECISIONS.md),
текущий API и будущие границы — [API-CONTRACT.md](API-CONTRACT.md).
Рабочая интеграция 1С, реальные заказы и деньги пока отсутствуют.

## Текущий demo

NestJS/TypeScript, PostgreSQL/Prisma, shared Zod-контракты. Реализованы публичные
категории/карточки, demo auth и сессии, сохранённый staff-редактор и bounded
фотографии WebP. Публичная проекция явно исключает цены/наличие и бинарные данные.
Схема/миграции и tests находятся в apps/api; код demo не является production-допуском.

Отдельная админка исключена из целевого продукта. Существующие manager endpoints
и редактор сохраняются как тестовый стенд, а не новая система работы сотрудников.
Их права не заменяют согласованный процесс одобрения/назначения клиентов в 1С.

User и AuthUser содержат `commercialAccessStatus` со значениями
`pending|approved|rejected|revoked`; миграция задаёт безопасный default pending,
регистрация принудительно создаёт pending. Login/me читают актуальное состояние БД. Регистрация принимает только телефон/пароль; покупатель
не задаёт роль, одобрение, контрагента или менеджера. Самостоятельного endpoint
одобрения не добавляем. Описание проверенного результата — в HANDOFF.md.

## Целевой первый сквозной процесс

1. Каталог/цены/наличие поступают из 1С с проверяемой идентичностью и актуальностью.
2. Гость или ожидающий одобрения клиент видит только публичную карточку.
3. Менеджер в 1С забирает свободного клиента, одобряет и подтверждает контрагента;
   backend получает согласованный сигнал. Как именно — устанавливает обследование.
4. Одобренный клиент выбирает метры/рулоны. Сервер применяет правила и проверяет
   1С; заявка с неизвестным результатом обмена не выдаётся за принятый заказ.
5. Заказ попадает в 1С и согласуется менеджером. Полный процесс изменений пока
   открыт; не вводить обязательное повторное клиентское принятие из старого ТЗ.
6. 100% предоплата картой или по счёту подтверждается доверенным источником;
   затем 1С формирует отправление/трек. Доставка отдельно перевозчику при получении.

Ни корзина, ни ожидающий оплаты заказ не резервируют товар: резерв исключён.
Повторная проверка перед оплатой не гарантирует наличие до списания; нужны
согласованные сценарии дефицита и компенсаций. Не обещать устранение гонки.

## Правила наличия и цены

- Color/Color Ultima: порог ≤2 целых рулонов считается по участвующим складам
  одного SKU и запрещает любые отрезы, включая готовые. Доступные целые рулоны
  продаются при положительном достаточном количестве независимо от этого порога.
- Отрезы учитываются в 1С по метражу. Варианты 1–18 м с шагом 1 м — выбор клиента,
  а не предположение о наличии; «Есть / Нет» строится по конкретным данным 1С.
- Длина рулона per-SKU. Сумма обрезков не доказывает непрерывную нужную длину.
- Участие складов, ширина, разнотон/партии, ценовая единица, НДС и округление
  ещё не согласованы. Отсутствующие сведения не заполняются выдуманными значениями.
- Разные прайсы не нужны. Цена и правила вычислений контролируются сервером/1С,
  не приходят доверенными из формы покупателя. Денежные вычисления без binary float.

## Предлагаемые области данных

Это карта проектирования, не список уже существующих таблиц.

| Область | Ответственность |
|---|---|
| Сессия/пользователь | Аутентификация, текущий статус коммерческого доступа, безопасная связь с внешним клиентом |
| Контрагент/назначение | Подтверждённые внешние ID, одобрение/отзыв и одно текущее назначение по процессу 1С |
| Проекция каталога | SKU/категории/характеристики/фото/размеры, внешняя версия и источник |
| Закрытая проекция предложений | Цена, метражи/рулоны, правила, снимок/свежесть только для одобренных |
| Обмен | Inbox/outbox, correlation ID, checkpoint, полное/частичное обновление, повторы/ошибки |
| Заказ | Внешний ID, владелец, переданные условия и установленный результат принятия 1С |
| Оплата | Неизменяемые попытки, доверенные финансовые события, сверка и возвраты |
| Доставка | Выбранный ПВЗ/адрес, отдельно оплачиваемая перевозка, отправление и трек из 1С |
| Аудит/уведомления | Кто/когда изменил значимое состояние; SMS/push с повторяемой доставкой |

Таблица Reservation и TTL не являются частью нового требования. Не создавать
скрытое удержание склада под видом внутренних таблиц. Возможности и поля 1С
подтверждаются перед миграциями бизнес-сущностей.

## Согласованность и безопасность

- Стабильные внешние ID, не сопоставление только по названию/телефону.
- Одобрение и отзыв влияют на каждый закрытый запрос; роль и менеджер не доверяются
  клиенту. Публичный/shared cache не содержит закрытых DTO.
- Назначение свободного клиента атомарно в согласованном источнике: два менеджера
  не получают одновременно владение. Повтор команды не перезакрепляет клиента.
- Входящий снимок валидируется до публикации. Неполный снимок не обнуляет отсутствующие
  товары; старое событие не затирает новое. Ошибка оставляет последний успешный снимок.
- Исходящая команда имеет устойчивую идентичность и контролируемые повторы. Timeout
  с неизвестным исходом требует сверки, а не второго заказа или списания.
- Сетевые вызовы не удерживают длинную SQL-транзакцию. Факт оплаты не теряется
  при сбое уведомлений; финансовые события отделены от исполнения заказа.
- Приватные данные/секреты не попадают в логи, browser storage, RSC или сообщения CI.

При stale/unavailable предлагается оставить просмотр последнего каталога и
блокировать оформление/оплату; порог/восстановление ещё согласуются. Диагностика
оператора должна показывать безопасное состояние обмена без отдельной продуктовой
админки: способ доступа согласовать с программистом/эксплуатацией 1С.

## Следующая проверяемая поставка

Обследование → контракт и обезличенные примеры → read-only обмен на тестовой 1С →
ACL одобрения/отзыва → один идемпотентный заказ и менеджерские статусы → sandbox
карты/счёта, ПВЗ/трек и SMS/push. Fake adapter помогает разработке, но не заменяет
реальную приёмку. Срок зависит от полученных возможностей и материалов заказчика.
