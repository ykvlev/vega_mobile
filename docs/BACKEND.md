# VEGA — backend и данные

Статус: проектирование. API, схема базы, миграции и интеграция ещё не реализованы
и не проверены. Документ описывает предлагаемые контракты первого сценария,
а не существующие endpoints. Нормативные DTO, переходы и протокол восстановления
зафиксированы в [API-CONTRACT.md](API-CONTRACT.md); последние бизнес-решения —
в [DECISIONS.md](DECISIONS.md).

## Граница ответственности

Предлагаемый стек: NestJS, TypeScript, PostgreSQL, Prisma; REST `/api/v1`, OpenAPI.
Сервер отвечает за права, цены, доступность, резервы, заказы и назначения.
Мобильное приложение и админка не обращаются к базе или 1С напрямую.
Redis/BullMQ подключаются для фоновых операций; Redis не является источником
остатков и не заменяет транзакции PostgreSQL.

Первый сквозной сценарий: администратор создаёт товар → клиент просматривает
публичную карточку → регистрируется/входит и получает цены/остатки → проходит актуальную проверку доступности 1С и передаёт
заказ на согласование → менеджер подтверждает финальные условия → клиент
принимает их → сервер проверяет наличие и согласованный резерв в 1С → клиент
вносит 100% предоплаты картой либо по счёту → сервер подтверждает поступление →
разрешается отправка. Онлайн-оплата картой обязательна в первом релизе;
счёт юрлица является отдельным способом, не proof через скриншот.
Демонстрационный режим работает только с явно тестовыми данными и sandbox-оплатой.
Рабочие продажи без проверенной интеграции 1С недопустимы.

## Подтверждённое и открытое

- Поддерживаются физлица и организации/ИП.
- Гость видит каталог без цен и остатков; они доступны после регистрации и входа.
- Онлайн-оплата входит в обязательный первый релиз; до неё менеджер согласует
  заказ. Предоплата 100%, отправка после подтверждения поступления. Карты и счёт
  юрлица поддерживают разные источники подтверждения оплаты.
- Заказ зависит от 1С: отсутствующий в 1С товар либо недостаточный доступный
  остаток нельзя заказать. Локальный снимок не гарантирует наличие.

- Длина полного рулона задаётся у товара, а не общей константой.
- Продажа плёнки возможна метрами либо полными рулонами.
- При двух полных рулонах и меньше нарезка из полных рулонов запрещена;
  готовые отрезы продавать можно. Отрез должен покрывать заказ: сумма несвязанных
  обрезков не заменяет требуемую непрерывную длину. Несколько отрезов — явный выбор.
- Начальный вход: телефон + пароль; SMS позднее. Телефон при регистрации без SMS
  не считается автоматически подтверждённым. Требования защиты — SECURITY.md.
- Минимум/шаг нарезки, область порога по складам, срок резерва и способ его
  согласования с 1С остаются открытыми.
- Одинаков ли размер всех рулонов одного артикула и учитывает ли 1С отдельные
  рулоны — неизвестно. Нельзя вывести доступность отреза только из общего метража.
- Назначение клиента активному менеджеру по очереди — предложение из ТЗ;
  постоянное закрепление и ручное переназначение также требуют финального принятия.

До выбора правил спорные сценарии помечаются как неподдержанные в демонстрации;
их нельзя молча разрешать либо выдавать тестовые остатки за реальные.

## Модель данных

| Сущность | Ключевые поля и ограничения |
|---|---|
| User | UUID, роль, подтверждённые контакты, состояние, даты; отдельная сущность сессии |
| CustomerProfile | userId, тип физлицо/организация, имя и контактные данные |
| Organization | профиль, наименование, ИНН, применимый КПП, юридический адрес |
| Address | владелец, структурированный адрес; отдельный снимок в заказе |
| ManagerAssignment | клиент, менеджер, даты, причина; одно текущее назначение |
| Category | название, порядок, видимость |
| Product | артикул, название, категория, состояние, описание, внешняя идентичность |
| ProductVariant | продаваемый SKU, цвет/фактура, widthMm, rollLengthMm, единицы продажи |
| ProductMedia | файл в объектном хранилище, роль, порядок; без binary в PostgreSQL |
| Price | SKU, валюта, вид цены, целая сумма, период/версия |
| Warehouse | внутренний ID, внешний ID, доступность для оформления |
| StockPosition | SKU, склад, вид остатка, физическое количество, зарезервированное количество, версия, источник и время обновления |
| RollPiece | при необходимости: целый/открытый рулон или отрез, исходная и доступная длина; включается после обследования |
| Reservation | заказ, количество/единица, active/released/consumed/expired, expiresAt, версия, состояние подтверждения и идентификатор обязательства в 1С |
| Order | номер, клиент, менеджер, исполнение, фиксированные суммы/валюта, даты и снимки контактов/доставки; оплата отдельной машиной состояний |
| CartLine | lineId, cartId, skuId, unit, количество; unique(cartId, skuId, unit) |
| OrderItem | собственный lineId, снимок SKU/названия/цены, единица покупки, количество, длина рулона, сумма |
| DeliveryTerms | тип/перевозчик, получатель/адрес или ПВЗ, стоимость/валюта и момент оплаты, deliveryVersion |
| OrderApproval | managerId, approvedAt, orderVersion, deliveryVersion, amount/currency, финальные условия; отдельное принятие клиентом |
| OrderEvent | прежнее/новое состояние, исполнитель, время, причина |
| PaymentAttempt | заказ, провайдер/merchant account, внутренний/внешний ID, серверные сумма/валюта, состояние/версия, ключ идемпотентности |
| PaymentEvent | внешний ID события либо документированный ключ дедупликации, время, результат проверки и обработки |
| Refund | paymentId, сумма, причина, внешний ID, состояние, идемпотентность, исполнитель |
| ReconciliationRun | область/период сверки, расхождения, результат и ответственный |
| IdempotencyRecord | субъект, операция, ключ, hash запроса, результат и связанный заказ |
| OutboxEvent | событие, payload без лишних персональных данных, доставка и попытки |
| IntegrationMapping | система, тип сущности, внешний ID, внутренний ID, версия |
| SyncRun | направление, область, начало/конец, checkpoint, результат и безопасная ошибка |
| AuditEvent | субъект, действие, объект, время, requestId; не хранит секреты |

Товар и SKU могут совпадать в интерфейсе для простых товаров; цены и остатки
привязаны к конкретной продаваемой позиции. Длина рулона относится к этой позиции.
Связанные с заказами товары архивируются. Для заказа сохраняются исторические
снимки, чтобы правка карточки не меняла документы прошлого.

## Единицы и точность

Предлагается хранить деньги как целое число минимальных единиц валюты, длины —
целое число миллиметров, количество рулонов/штук — целое неотрицательное число.
В JSON большие целые передавать десятичными строками, не полагаться на float.
Например, `rollLengthMm: "15000"`, `unitPriceMinor: "125000"`, `currency: "RUB"`.

Цена за метр имеет явный базис `priceBasisMm: "1000"`. Расчёт позиции выполняется
сервером с точной арифметикой и согласованным округлением до минимальной единицы
валюты. Предложение: округление half-up один раз на сумму позиции; итог — сумма
позиций. Налоги, включённость НДС, скидки и политика округления подлежат согласованию.
Цена рулона может быть отдельной: её нельзя автоматически считать равной цене
метра, умноженной на длину, если прайс задаёт другое правило.

Минимальный отрез и шаг задаются отдельно. Ширина плёнки не участвует в переводе
погонных метров в квадратные без отдельной единицы продажи. Никакого сравнения
денег и длин с допусками floating point.

## Предлагаемые REST-контракты первого сценария

Публичные DTO отделены от приватных. `products` содержит только открытые
характеристики и изображения; `product-offers` требует входа. Запрет раскрытия
распространяется на списки, поиск, фильтры/агрегации, HTML/SSR, JSON-LD, экспорт,
аналитику и ошибки. Поле hidden и скрытая кнопка не являются защитой данных.
Гостю недоступны фильтры/сортировки цены и наличия, stock freshness и вычисленная
из склада доступность нарезки. Публичные изображения/описания не содержат цен.

Приватные offers/profile/quotes/orders используют `Cache-Control: private,
no-store`, не попадают в shared CDN/Next.js cache. Публичный кэш никогда не
наполняется приватным DTO. Клиентский query cache изолирован по пользователю и
очищается при выходе; закрытые поля не сохраняются в гостевом persisted/offline
cache. Данные физлица не появляются при входе другого аккаунта на том же устройстве.

| Метод и путь | Назначение |
|---|---|
| GET /api/v1/categories | Видимые категории |
| GET /api/v1/products | Фильтры categoryId, query, cursor, limit; ограниченный размер страницы |
| GET /api/v1/products/:id | Только публичная карточка без цены и остатков |
| GET /api/v1/product-offers?skuIds=... | Только после входа: цены, остатки, freshness и доступные способы покупки |
| POST /api/v1/admin/products | Создание товара/SKU; право catalog:write |
| PATCH /api/v1/admin/products/:id | Правка с проверкой версии; архивирование отдельным полем |
| POST /api/v1/admin/stock-adjustments | Только для локального источника: корректировка с причиной и аудитом |
| GET /api/v1/me | Профиль и назначенный менеджер |
| GET /api/v1/cart | Текущая серверная корзина; без резерва |
| POST /api/v1/cart/items | Установить количество по SKU+unit, получить lineId; метры/рулоны отдельные строки |
| PUT /api/v1/cart/items/:lineId | Изменить количество существующей строки; SKU/unit неизменяемы |
| DELETE /api/v1/cart/items/:lineId | Удалить только указанную строку |
| POST /api/v1/order-quotes | Актуальная доступность 1С обязательна; расчёт/версии без резерва |
| POST /api/v1/orders | Новая проверка доступности 1С, затем заказ на согласование с Idempotency-Key; при отказе Order не создаётся, резерв не обещается |
| GET /api/v1/orders | Заказы текущего клиента |
| GET /api/v1/orders/:id | Детали с проверкой владельца/полномочий |
| GET /api/v1/admin/orders | Только разрешённые сотруднику заказы |
| POST /api/v1/admin/orders/:id/transitions | Разрешённый переход с причиной и expectedOrderVersion |
| POST /api/v1/admin/orders/:id/approvals | Менеджер подтверждает финальные версии состава, суммы и доставки |
| POST /api/v1/orders/:id/acceptance | Клиент принимает согласованную версию условий |
| POST /api/v1/orders/:id/payment-attempts | Владелец; согласованные версии, 1С gate, 100% суммы; метод card/business_invoice, Idempotency-Key |
| GET /api/v1/orders/:id/payment | Подтверждённое серверное состояние, без секретов провайдера |
| POST /api/v1/webhooks/payments/:provider | Отдельная проверка подлинности события провайдера |
| POST /api/v1/admin/payments/:id/refunds | Специальное право, причина, сумма, аудит, Idempotency-Key |

Пути и DTO фиксируются OpenAPI до реализации клиентов по API-CONTRACT.md.
Количество вложено в quantity: `{unit: "meter", quantity: {lengthMm: "5000"}}`
либо `{unit: "roll", quantity: {count: 1}}`; несовместимые поля отклоняются.
Точные состав и формат auth endpoints
зафиксированы в API-CONTRACT.md: телефон + пароль, SMS позже. Тестовый вход
запрещён в production; нет обязательной зависимости bootstrap от SMS-провайдера.

Корзина с расчётом, quote, заказ и оплата доступны только вошедшему клиенту.
Гостевой подбор SKU не получает закрытые данные.

Quote и submit в production требуют актуальной доступности 1С; старый snapshot
не разрешает создать коммерческий заказ. Между submit и оплатой наличие не
гарантируется, поэтому check/reserve повторяются перед оплатой.

Quote возвращает позиции, серверные цены/суммы, доступность, предупреждения,
версию расчёта и срок действия. Истечение quote не означает наличие резерва.
При изменениях создание заказа возвращает конфликт и новый расчёт для явного
подтверждения, а не оформляет заказ по незаметно изменённой цене.

Ошибки имеют стабильные коды и requestId по API-CONTRACT.md. В частности,
409 STOCK_UNAVAILABLE — SKU/достаточности нет; 503
INVENTORY_CONFIRMATION_UNAVAILABLE — актуальность/доступность 1С не подтверждена.
Коды закрытых данных не раскрывают гостю цены, остатки или чужие объекты.

## Транзакция заказа и резервов

1. Проверить авторизацию/формат; найти исходную операцию по области идемпотентности
   и вернуть её сохранённый результат до повторной бизнес-валидации.
   Для новой операции до создания Order подтвердить актуальную доступность в 1С.
   Нет SKU/остатка, stale/unavailable — отказ, сохраняется корзина; можно сохранить
   только техническую запись попытки, не коммерческий заказ/замаскированную заявку.
   Проверка submit не резервирует: перед оплатой необходимы повторный check/reserve.
2. Начать транзакцию. Захватить/проверить уникальный IdempotencyRecord.
3. Заблокировать необходимые строки остатка в стабильном порядке либо выполнить
   атомарное условное списание доступности; выбрать и проверить конкретную стратегию
   через concurrency-тесты. Обработка deadlock/serialization failure ограничена.
4. Прочитать актуальные цены, доступность, freshness и правила нарезки. Учитывать
   активные резервы. Не считать общий метраж числом полных рулонов.
5. Сверить клиентский расчёт. При конфликте не создавать заказ и резерв.
6. Создать локальную подготовку заказа, снимки позиций, предварительные локальные
   резервы, назначение менеджера при необходимости, историю и outbox-событие
   в одной транзакции. Они не подтверждают право на товар вне локальной системы.
7. Сохранить результат идемпотентности и commit. Уведомления и обмен выполнять
   после commit через outbox; сбой отправки не откатывает существующий заказ.

Инварианты: резерв не превосходит физически доступное количество; один резерв
освобождается или потребляется не более одного раза; отмена и отгрузка конкурентно
проверяют текущую версию заказа. Изменение статуса не допускает произвольного
прыжка. Отмена/истечение освобождают резерв транзакционно и идемпотентно.

Для онлайн-оплаты срок неоплаченного резерва обязателен. Значение TTL,
допустимость частичного исполнения и момент потребления согласуются до пилота.
API возвращает expiresAt; локальный countdown не определяет исход. Истечение,
webhook, отмена и новая попытка блокируют согласованные строки/проверяют версии.
Оплаченный резерв не истекает по таймеру неоплаченного. Не задавать произвольный
production TTL без проверки срока обязательства в 1С и ограничений провайдера.

Вышеописанная PostgreSQL-транзакция обеспечивает только локальную атомарность.
Она не является распределённой транзакцией с 1С. После согласования менеджером и клиентом проверенный при submit заказ
получает состояние inventory_confirmation_pending; внешнее подтверждение
выполняется вне длительной SQL-транзакции, с корреляцией и компенсациями.
В awaiting_payment заказ переводится только после подтверждения менеджером,
принятия клиентом финальной версии и подтверждённого обязательства 1С.
Его семантика и доступный способ резерва должны быть доказаны на конфигурации
заказчика. Если защиты от продажи другими каналами получить нельзя, платёжный
gate остаётся BLOCKED; одной свежей проверки недостаточно для обещания резерва.

Нормативный recovery: повторить тот же POST с тем же persistent Idempotency-Key
и тем же canonical payload. Клиент сохраняет ключ/операцию до первого запроса
в безопасном per-account хранилище и не меняет после timeout/перезапуска.
Отдельного lookup по ключу нет. Завершённая операция возвращает прежний ресурс
до повторной бизнес-валидации истёкшего quote. В обработке — 409
REQUEST_IN_PROGRESS + Retry-After, повтор тем же POST. Другой payload — 409
IDEMPOTENCY_CONFLICT. Привязка к пользователю и операции обязательна.

Срок хранения ответа и tombstone/связи с заказом — явная настройка с минимальным
поддержанным recovery window. Значения и политика хранения требуют принятия до
production. Ключ не превращается в новую операцию после чистки ответа: сохранённый
tombstone возвращает исходный ресурс либо IDEMPOTENCY_RECORD_EXPIRED и безопасный
сценарий поддержки. Автоматическая выдача нового ключа запрещена при неизвестном
исходе. Подробности и критерии документарного закрытия — API-CONTRACT.md.

## Онлайн-оплата, возвраты и сверка

Подробный предлагаемый процесс: [PAYMENTS.md](PAYMENTS.md). Платёж имеет отдельную
машину состояний; исполнение заказа — другую. Return URL, success callback SDK,
скриншот и ручная правка менеджера не доказывают оплату. Сумму, валюту и состав
вычисляет сервер. До начала оплаты нужны окончательные доставка/налоги/скидки,
подтверждение менеджером и принятие клиентом тех же версий условий/доставки,
100% суммы к предоплате и действующее подтверждение достаточного остатка/резерва
в 1С. При stale/unavailable, отсутствии SKU или недостатке остатка — отказ gate,
без списания и без перенаправления на оплачиваемый checkout.

VEGA не принимает PAN/CVV: используется hosted checkout/SDK выбранного провайдера.
До внешнего вызова сохраняется PaymentAttempt со стабильным ключом. Timeout —
не отказ: сначала восстановить существующую попытку через провайдера, не создавать
второе списание. Сумму после старта не менять молча. Новая попытка допустима после
доказанного завершения прежней без списания либо управляемого восстановления.

Подлинность webhook проверяется официальным механизмом конкретного провайдера:
подпись, timestamp/replay и/или серверная проверка API. IP allowlist недостаточен.
Проверяются merchant account, внешний payment ID, сумма/валюта и внутренний заказ.
Событие сохраняется надёжно до подтверждения приёма, обрабатывается идемпотентно;
pending не понижает succeeded из-за изменения порядка доставки. Неоднозначность
разрешается запросом текущего состояния провайдера, а не временем прихода webhook.

Поздний success после истечения резерва не разрешает отгрузку без товара. Сначала
проверяется и восстанавливается обязательство в 1С по согласованному протоколу;
если это невозможно — payment exception, запрет исполнения и контролируемый
возврат. Нельзя молча заменить товар. Локальная отмена не отменяет списание
у провайдера. Неизвестный исход сохраняется как unknown/reconciliation_required.

Возврат — отдельная идемпотентная операция с pending/succeeded/failed/unknown.
Формула лимита: succeededRefunds + pendingOrUnknownRefunds + newRefund
<= receivedAmount. Успешные возвраты не вычитаются повторно. Для полного/частичного
возврата сохраняются причина
и позиции по фискальным требованиям. Возврат денег сам по себе не возвращает
физически отгруженный товар на склад и не отменяет состояние исполнения.

Для счёта юрлица факт поступления подтверждается согласованным банковским/1С
источником либо уполномоченным сотрудником по проверенному поступлению с аудитом.
PDF счёта, платёжное поручение клиента и его скриншот не подтверждают получение.
Частичная оплата не разрешает отправку; излишек/неясное назначение — исключение.

Фоновая сверка восстанавливает пропущенные события, зависшие попытки, возвраты
и расхождения settlement. Изменения имеют аудит; ключи и карточные данные не
попадают в логи. Фискализация, чеки, налоги, продавец и применимые правила должны
быть согласованы; провайдер, ставки и юрисдикция ещё не определены.

## Права и назначения клиентов

Гость читает опубликованный каталог без цен/остатков. Зарегистрированный
вошедший клиент получает разрешённые offers и видит собственные профиль, корзину
и заказы. Менеджер видит назначенных клиентов и их заказы. Администратор управляет
всеми; catalog:write выдаётся отдельно. Правила применяются в API и запросах к БД,
а не только скрытием кнопок. Защита проверяется также для вложенных ресурсов,
экспорта и доступа к файлам.

Предлагаемая очередь назначения хранится в PostgreSQL. Создание первого назначения
сериализуется: блокировка состояния распределения, выбор следующего активного
менеджера, уникальное текущее назначение клиенту. При отсутствии менеджеров заказ
попадает в неназначенную очередь. Число менеджеров не фиксируется равным трём.
Переназначение имеет аудит. Политика прав на старые заказы при переназначении
требует отдельного решения; нельзя случайно оставить доступ прежнему сотруднику.

## Адаптер 1С

Конкретный протокол пока неизвестен. Внутренний интерфейс адаптера отделяет
получение номенклатуры/цен/остатков, передачу заказов и получение статусов.
Поддержку каждого направления подтверждать обследованием, не обещать её заранее.

- Выбрать источник истины отдельно для цены, физического остатка, резерва и статуса.
- Не вычитать локальный резерв повторно, если 1С уже включила его в доступность.
  Нужна согласованная модель подтверждения заказа и сверки резервов.
- Использовать стабильные внешние ID и таблицу соответствий; не сопоставлять по
  изменяемому названию. Учесть удаления/архивирование и повторные сообщения.
- Входящий снимок сначала валидировать, затем атомарно публиковать в согласованной
  области. Неполную выгрузку не трактовать как нулевые остатки всех отсутствующих SKU.
- Вести checkpoint, время успешного обновления и журнал без секретов/лишних ПДн.
- Повторять временные ошибки с ограничениями; недоставленные операции сохранять.
- Если SKU отсутствует в 1С, остатка недостаточно либо подтверждение недоступно/
  устарело — блокировать заказ и начало оплаты. Не заменять это оплачиваемой заявкой.
- Рабочий резерв требует подтверждённого протокола 1С; его атомарность и наличие
  нельзя предполагать. Согласовать дедупликацию, TTL и компенсацию после timeout.
- Для тестов использовать fake adapter с явно тестовыми данными и контрактные
  фикстуры. Доступ к рабочей 1С не нужен для unit-тестов и внешних PR.

## Минимальные проверки приёмки backend

Точность длин и сумм; разные длины рулонов; отклонение неверного шага; правило нарезки <=2 полных рулонов и разрешённые готовые отрезы; конкуренция за последний остаток; повтор после потери
ответа; повторная отмена; устаревшая цена; отсутствие двойного резерва при обмене;
разграничение ролей; конкурентное назначение менеджеров; архивирование товара
без изменения заказа; сбой уведомления после commit; повтор и неполная выгрузка 1С.
Отсутствие цены/остатка во всех guest payload и shared cache; выход/смена аккаунта;
отказ заказа и оплаты при отсутствии SKU/остатка/подтверждения 1С; поддельный,
повторный и переупорядоченный webhook; неверная сумма/валюта/merchant; timeout
после списания; гонка TTL/успех/отмена; поздний успех без товара; двойной возврат;
восстановление после потери webhook; независимость оплаты и исполнения;
метры+рулоны одного SKU в разных lineId; replay после перезапуска/истечения quote;
частичная оплата счёта; запрет отправки до 100%; недействительность оплаты старых
версий условий и доставки.

## Зависимости первого этапа

Архитектор фиксирует границы пакетов и OpenAPI-процесс. Мобильная команда и админка
согласуют contract-first DTO и коды ошибок. QA подтверждает конкурентные проверки
на настоящем PostgreSQL. Заказчик/специалист 1С уточняют единицы, источники истины,
минимум/шаг нарезки, резервы, цены/НДС и свежесть данных до реальных заказов.
Неизвестные провайдер, сроки и конфигурация 1С не блокируют bootstrap и изолированные
тесты. Production блокируют непроверенные 1С/резервы, merchant/источник банковских
поступлений, фискальная схема и обязательные параметры коммерческого процесса.
Документарная согласованность не является прохождением runtime-проверок.
