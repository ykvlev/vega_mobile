# VEGA: выпуск мобильных приложений

Статус: план. Приложения, EAS-проект, аккаунты магазинов, подписи и пайплайны
ещё не настроены и не проверены. Документ не подтверждает готовность релиза.

## Роль релиз-инженера

Отвечает за воспроизводимые подписанные сборки Android/iOS, версии, каналы,
передачу в тестирование, выпуск и восстановление после неудачного обновления.
Не заменяет QA и безопасника: открытый обязательный gate запрещает продвижение.

## Подготовка

- Подтвердить владельца Expo/EAS-проекта и аккаунтов Apple Developer,
  App Store Connect и Google Play Console; предоставить минимальные права.
- Закрепить bundle identifier/applicationId и разделение staging/production.
- Выбрать EAS Build либо собственные runners; сборка iOS требует macOS/Xcode
  или соответствующего облачного сервиса. Проверить тарифы и лимиты.
- Настроить development, preview/internal и production профили сборки.
- Подготовить политику конфиденциальности, сведения о сборе данных и разрешениях,
  материалы карточек магазинов, возрастной рейтинг и контакты поддержки.
- До объявления готовности проверить актуальные требования магазинов,
  включая обязательное тестирование, доступность аккаунта и целевые SDK.

## Доступы и секреты

Сначала проверить существующие bindings и доступы без вывода значений.
Ключи подписи, provisioning profiles, App Store Connect API key, Google Play
service account и CI-токены размещаются только в защищённых настройках EAS/CI
либо выбранном хранилище секретов. Не хранить их в Git, логах и артефактах.
PR из внешних веток не получает релизных доступов. Ограничить полномочия,
задокументировать владельца, восстановление и ротацию; не запрашивать значения
в чате. Клиентская конфигурация, встроенная в приложение, не является секретом.

## Путь кандидата релиза

1. Зафиксировать commit SHA, lockfile, toolchain, конфигурацию, версию API и
   release ID; все обязательные проверки должны иметь PASS.
2. Собрать подписанные Android/iOS-артефакты из одного исходного commit.
   Зафиксировать build IDs, checksum/digest и используемое окружение.
3. Передать iOS в TestFlight, Android — в Google Play internal testing.
   Проверить установку и обновление на согласованных реальных устройствах.
4. QA проверяет вход, каталог, метры/рулоны, оформление, восстановление после
   обрыва, уведомления, совместимость API и 3D/fallback на выбранном артефакте.
5. Получить явное одобрение ответственного за production; убедиться в готовности
   сервера, поддержки и мониторинга. Отправка на проверку магазина и фактическая
   публикация фиксируются отдельно от успешной сборки.
6. Выпускать постепенно, когда магазин поддерживает такой режим; наблюдать
   crash/errors и ключевые сценарии. Порог остановки и окно наблюдения определить
   до выпуска по согласованным метрикам, а не придумывать после сбоя.

## Версии и OTA

- Пользовательская версия и уникальные номера Android versionCode / iOS
  buildNumber связываются с release ID; повторный выпуск не переиспользует
  неподходящий номер. Номера и конфигурация хранятся воспроизводимо.
- Expo Updates рассматривается только после настройки и проверки runtimeVersion.
  Новые нативные зависимости, разрешения или изменение native runtime требуют
  новой совместимой сборки, а не доставки через OTA.
- Каналы staging/production разделены. OTA публикуется в правильный runtime и
  канал после проверки на совместимом бинарном приложении и отдельного gate.
- API сохраняет совместимость с поддержанными старыми версиями мобильного клиента.
  Нельзя считать, что все пользователи установили новый бинарный релиз.

## Ограничения отката

Установленный store binary нельзя мгновенно заменить старой версией как серверный
образ. При сбое остановить rollout, при возможности снять проблемное обновление
с дальнейшего распространения и подготовить исправляющий релиз. Доступность этих
операций проверяется для выбранного магазина.

Совместимый OTA можно вернуть к проверенной версии по испытанному сценарию;
переход между несовместимыми runtime запрещён. Откат сервера и схемы БД должен
сохранять поддержку уже установленных клиентов; destructive downgrade не является
автоматическим шагом мобильного rollback.

## Доказательства готовности

- Есть ссылки на CI-run, commit, build ID и точный проверенный артефакт.
- Подтверждены подпись, установка/обновление, окружение и разрешения приложения.
- QA и security gates закрыты, критические сценарии выполнены на устройствах.
- Приложены результаты TestFlight/internal testing и готовность store metadata.
- Проверены доставка crash-report с release ID и совместимость source maps.
- Зафиксированы одобрение, план распространения, алерты и ответственный за откат.
- Сценарий остановки rollout/совместимого OTA rollback испытан до production.

Пока эти доказательства отсутствуют, статус — BLOCKED для выпуска, но подготовка
проекта и независимая разработка могут продолжаться.
