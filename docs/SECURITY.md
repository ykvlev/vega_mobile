# VEGA: безопасность и право блокировки релиза

Статус: начальный review проектных документов. Приложения, конфигурация CI/CD
и инфраструктура ещё не реализованы. Подтверждённых уязвимостей кода по этому
review нет; это не заключение об отсутствии уязвимостей в будущей реализации.
Внешние системы не сканировались, эксплуатация и проверка production не проводились.

## Роль безопасника

Независимо проверять угрозы, код и фактическую конфигурацию на каждом затрагиваемом
этапе. Указывать конкретный актив, границу доверия, условие атаки, последствия,
воспроизводимые доказательства и исправление. Не называть гипотезу найденной
уязвимостью и не подменять review общим списком страшных сценариев.

Подтверждённая critical/high уязвимость блокирует выпуск затронутого компонента.
Нет доказательства выполнения обязательной security-проверки — gate не пройден.
Это не запрещает независимую работу над другими компонентами или ограниченный
локальный прототип без реальных данных и внешнего доступа.

## Активы, противники и границы доверия

| Актив | Основные угрозы | Граница |
|---|---|---|
| Аккаунты и сессии | Перебор пароля, захват аккаунта, кража/повтор токена; OTP на будущем этапе | Клиент → Identity API; SMS позже |
| Контакты, адреса, реквизиты | Доступ к чужим объектам, массовый экспорт, утечка логов | Роли → API → БД/экспорт/backup |
| Цены, остатки и заказы | Подмена клиентом, гонка, двойной резерв/отмена | Клиент → транзакции API → 1С |
| Медиа и 3D | Вредоносный файл, XSS, SSRF, истощение памяти | Загрузка → обработчик → S3 → WebView |
| Артефакты и ключи публикации | Утечка секретов, вредоносный PR/пакет, подмена сборки | GitHub → runner → registry → deploy/EAS |
| Обмен 1С | Поддельный/повторный пакет, избыточный доступ, утечка учётных данных | Адаптер → доверенный endpoint 1С |

Рассматривать неавторизованного пользователя, клиента с собственным аккаунтом,
сотрудника с ограниченными правами, скомпрометированный аккаунт/пакет и внешний PR.
Мобильный клиент, его локальные данные и сообщения WebView не считаются доверенными.

## Обязательные проверки

| Область | Что проверить | Доказательство |
|---|---|---|
| Пароль (первый релиз) | Argon2id с солью и параметрами по актуальным рекомендациям, rate limits, одинаковые ответы, отсутствие пароля в логах; проверяемое владение/восстановление до production | Негативные тесты login, смены/отзыва сессий и recovery; проверить параметры hash и исключение credential из DTO |
| OTP (будущий этап) | TTL, одноразовость, лимиты, бюджет SMS, безопасные ответы без enumeration; не prerequisite bootstrap | После подключения: sandbox и тесты неверного/истёкшего/повторного кода |
| Сессии | Краткая access-сессия, отзыв и rotation refresh, reuse detection при применении rotation, выход, блокировка пользователя | Тесты refresh/revoke/logout; секреты отсутствуют в логах |
| Сотрудники | Отдельная выдача ролей, отсутствие самоповышения, MFA для привилегированных ролей до production | Негативные API-тесты и проверка конфигурации входа |
| Cookie/admin | HttpOnly, Secure, согласованный SameSite, CSRF для мутаций, явные CORS origins, защита от XSS | Проверка заголовков и API-тесты cross-site запросов |
| Объектные права | Заказы, клиенты, адреса, файлы, экспорты, вложенные ресурсы; переназначение менеджера | Матрица guest/customer/manager/admin и прямые запросы чужих ID |
| Серверный ввод | Whitelist полей, пределы размера/пагинации, запрет mass assignment, безопасные запросы БД | Тесты лишних полей, роли/цены из payload, неверных типов и больших запросов |
| Бизнес-операции | Цена из доверенного источника, scoped idempotency key, гонки резервов, повторная отмена | Конкурентные тесты PostgreSQL и попытки использовать чужой ключ |
| ПДн | Минимизация, сроки хранения, ограничение экспорта, redaction, удаление/обезличивание по согласованным правилам | Review полей/логов/артефактов и тест разграничения экспорта |
| Устройства | SecureStore для refresh, отсутствие credentials в JS bundle, очистка приватного кэша при logout | Проверка сборки/хранилищ и тест смены аккаунта |
| Загрузки | Авторизация, лимиты размера/размерности/числа, проверка сигнатуры, безопасные имена и типы | Негативные тесты файлов и resource limits обработчика |
| Обработка файлов | Изолировать парсеры; не исполнять загруженное; private ACL по умолчанию, публикация только проверенного медиа | Конфигурация worker/S3 и тест прямого доступа к private объекту |
| Текст/изображения | Санитизация rich text, запрет активного SVG либо безопасная обработка, Content-Type/nosniff | XSS-регрессии и проверка response headers |
| WebView | Собственная сцена, allowlist навигации/ресурсов, строгая схема и список bridge-команд, отсутствие токенов в bridge | Негативные bridge-тесты и тест внешней навигации на устройствах |
| 3D-ресурсы | Запрет произвольных внешних URI в моделях, лимиты моделей/текстур, безопасный fallback | Набор malformed/oversized asset tests и профилирование устройств |
| SSRF | Не загружать сервером пользовательские URL без политики; блокировать loopback/private/link-local, redirects и DNS rebinding | Тесты загрузчика, если такой функционал введён; иначе явно N/A |
| 1С | TLS, сервисная аутентификация, минимальные права, schema/size limits, replay/idempotency, безопасные retries | Контрактные тесты sandbox и review прав сервисного аккаунта |
| CI supply chain | SHA-pinned actions, frozen lockfile, secret scan, dependency/image audit, минимальные permissions, изоляция fork | Реальные workflow runs и проверка настроек GitHub |
| Deploy | Проверенный digest, защищённый environment, отдельные runtime/CI credentials, OIDC по возможности | Связь commit → artifact → staging → production и запись approvals |
| Инфраструктура | БД/Redis без публичного доступа, TLS, отдельные окружения/доступы, секреты в защищённом settings | Review конфигурации и разрешённая проверка доступности |
| Восстановление | Шифрование backup, ограничение доступа, срок хранения, тест restore, отзыв скомпрометированных ключей | Протокол восстановления и учебного инцидента |

Антивирусная/дополнительная проверка файлов выбирается по разрешённым типам и
угрозам; отсутствие такого средства нельзя компенсировать доверием к расширению.
Публичный каталог не означает публичность персональных вложений и экспортов.
Согласование юридических правил ПДн не заменяет технические проверки и наоборот.

## Gates по этапам

1. **Bootstrap:** без секретов/реальных ПДн, зависимости закреплены, secret scan и
   безопасный CI; тестовые credentials недоступны production.
2. **Каталог/API:** валидация, ACL записи, безопасные медиа и опубликованный контент.
3. **Аккаунты/заказы:** вся ролевая матрица, сессии, CSRF, идемпотентность и гонки.
4. **3D/1С:** отдельные проверки соответствующих границ до включения функций.
5. **Production:** выполнены все применимые проверки, проверены backups/restore,
   наблюдение, секреты и права, нет открытых critical/high; аудит связан с релизом.

Нативную безопасность, фактические ACL облака и GitHub protections нельзя считать
проверенными только по YAML, unit-тестам или тексту документов.

## Блокеры и закрытие дефекта

Примеры подтверждённых release blockers: обход авторизации; чтение чужих ПДн;
произвольное повышение роли; production-секрет в артефакте; выполнение кода через
загрузку; доступ fork к deploy credentials; поставка подменённого артефакта.
Серьёзность CVE определяется применимостью и экспозицией, а не только наличием
номера в отчёте. До проверки применимости потенциальная high не отмечается PASS.

Карточка дефекта: ID, компонент/версия, уровень и обоснование, безопасные шаги
воспроизведения, наблюдаемый/ожидаемый результат, владелец, критерии исправления.
Не помещать реальные токены или чужие данные в отчёт. Исправление закрывается
повторной независимой проверкой на конкретном commit/artifact и регрессией.
Закрытие задачи автором без повторной проверки не снимает блокировку.

При споре безопасник передаёт оркестратору факты и оставляет статус BLOCKED либо
UNVERIFIED; молчание, дедлайн и успешная сборка не являются принятием риска.
Исключения низкой/средней серьёзности требуют явного решения уполномоченного
владельца, компенсирующих мер, срока и повторного review. Critical/high остаются
блокерами в рамках выбранной политики. Аварийные действия регистрируются отдельно
и не переименовываются в успешно пройденный gate.

## Результат начального review

В текущих документах предусмотрены правильные границы: server-side ACL,
scoped idempotency, secure sessions, outbox, изоляция test auth, защита fork CI.
Их реализация и настройки ещё не проверены. Требуют конкретизации до production:
MFA сотрудников, retention/deletion/export ПДн, upload pipeline, параметры хеша
пароля/сессий, проверка владения номером и recovery; OTP — при будущем подключении.
Также нужны правила private/public S3, 1С credentials и сетевой доступ, endpoints
мониторинга и incident runbook. Это открытые проектные риски, не найденные баги.

Можно продолжать bootstrap и демонстрационный сценарий с тестовыми данными;
security sign-off рабочего релиза пока НЕ ВЫДАН.
