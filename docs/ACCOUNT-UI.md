# VEGA: подключённый экран аккаунта

> Актуальные бизнес-правила: [DECISIONS.md](DECISIONS.md). Сотрудники целевого
> продукта работают в 1С; описанные desktop-функции остаются demo-стендом.



Рабочий web-срез поверх demo-auth API: `/account` (вход),
`/account?mode=register` (регистрация) и профиль после успешного входа.
Кнопка «Войти» в профиле дизайн-прототипа ведёт на этот экран.

Это пока web-интерфейс в мобильном размере, а не native-экран Expo.
Восстановление, SMS-подтверждение, коммерческие данные и покупки сюда не входят.

## Сессия и обработка форм

Только сервер обращается к `AUTH_API_URL`; допустим HTTPS либо HTTP loopback
для локальной разработки. URL не может содержать credentials, query/hash или
произвольный путь. Запросы используют фиксированные endpoints, no-store,
ограниченный timeout и не следуют redirects.

Bearer не возвращается в HTML/RSC, action state или localStorage. Cookie
`__Host-vega_session` всегда Secure, HttpOnly, SameSite=Lax, Path=/, без Domain.
Для браузера вне loopback нужен HTTPS; защита не ослабляется через заголовки.
Профиль каждый раз проверяется API. Выход очищает cookie после204/401 API;
при сетевом отказе сохраняется возможность повторить отзыв сессии.

Server Actions проверяют Origin/Host и не принимают cross-site или запросы
без Origin. Дополнительно действует встроенная проверка Next.js. Только одно
строковое поле phone и password допускается для credentials; metadata React
не отправляется в API. Сообщения ошибок не содержат введённые данные/токены.

## Проверка и запуск

Сборка: `pnpm build:contracts && pnpm --filter @vega/api build && pnpm build:admin`.
Браузерный набор: `pnpm test:account`. Требуется явная тестовая PostgreSQL БД.
Harness создаёт собственную случайную схему, поднимает API3181 и Next3102,
а также Next3103 с недоступным API для настоящего сценария сетевого отказа.
Счётчики очищаются только в этой схеме между независимыми browsercases;
проверки rate limiting остаются в отдельном auth integration наборе.

Auth traces не сохраняются, поскольку они могут содержать form body и cookie.
Скриншоты используют демонстрационные аккаунты. После завершения собственные
процессы и схема удаляются. CI job `account-ui` выполняет этот сценарий отдельно;
общий dependency audit и запрет релиза остаются без изменений.

Ограничение текущего demo: API видит сетевой адрес web-сервера, который
выполняет запросы от браузеров. Поэтому общий source-бюджет регистрации3/час
и входа20/15 минут разделяется пользователями одного BFF. Индивидуальный лимит
по телефону также действует. Перед публичным многопользовательским запуском
нужна проверенная схема доверенной передачи client source; произвольному
X-Forwarded-For доверие не добавлено и лимиты ради демонстрации не повышены.

## Локальный результат

Account browser7/7 прошёл без пропусков на настоящей цепочке PostgreSQL → Nest →
Next → Chromium. Проверены регистрация, вход, ошибочные/подменённые поля,
сохранение сессии, отзыв токена, возврат назад после выхода, CSRF и реальные
отказы API. После завершения временных account-схем осталось0. Получены
скриншоты login/register/profile на320/390px; копии390px находятся в docs/media.

Workspace types, lint, format и admin build прошли. Ранее в этом срезе также
прошли design7/7 и catalog7/7. Проверка чтения action-response ожидает его
завершения до reload, чтобы не отменять поток самим тестом. Assertion на
отсутствие секретов сохранён. Удалённый CI оценивается отдельно.

## Актуализация клиентского сценария

Корень web ведёт в /design-preview; ссылка в рабочую админку из профиля убрана.
Профиль показывает отдельный серверный статус одобрения. Новый аккаунт ожидает
одобрения менеджером, даже после успешного входа. Менеджер сам забирает клиента;
покупатель никого не выбирает. Сценарий назначения/одобрения через 1С ещё
не подключён. Формы не запрашивают managerId и не принимают статус одобрения.
