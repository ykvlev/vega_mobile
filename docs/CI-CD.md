# VEGA: CI/CD

Статус на 26 октября 2026: GitHub CI, сборки API/web/Expo export и demo-тесты
реализованы. Deployment, staging, native store builds и production не подключены.
Ниже текущие проверки отделены от целевого цикла доставки. Известный HIGH
node-forge остаётся обязательным audit blocker, не подавляется ради зелёного CI.
Целевые сотрудники работают в 1С; отдельная админка исключена, старый demo
продолжает регрессионно проверяться, пока остаётся в репозитории.

## Путь изменения

Локальная ветка → push → pull request → обязательные проверки → merge в main
→ сборка неизменяемых артефактов → staging → smoke/E2E → одобрение production
→ деплой → проверка → наблюдение либо откат.

## Локально

- Закрепить версии Node.js и pnpm; использовать единый lockfile.
- Перед коммитом: форматирование и lint изменённых файлов, проверка секретов.
- Перед push: typecheck и релевантные unit-тесты.
- Хуки ускоряют обратную связь; серверный CI повторяет обязательные проверки,
  поскольку локальные хуки можно обойти.
- Исключить из Git .env, ключи, базы, персональные данные и результаты сборок.
  Хранить только .env.example с именами и безопасными примерами.

## Push и pull request

GitHub Actions запускается для рабочих веток и PR; одинаковые запуски отменяются.
Обязательные проверки:

1. Frozen-lockfile установка, форматирование, lint, typecheck.
2. Проверка секретов в коммитах и зависимостей на уязвимости согласно политике
   серьёзности; исключения только с причиной, владельцем и сроком действия.
3. Unit-тесты бизнес-правил: метры/рулоны, порог нарезки, цены, роли, назначения.
4. Интеграционные тесты API с отдельной PostgreSQL; Redis при его введении и миграциями с нуля.
   Проверять идемпотентность, конкурентное закрепление клиентов и согласованный
   процесс дефицита без резерва ожидания оплаты. Реальные 1С/sandbox-проверки
   добавляются после доступа и контракта, не заменяются зелёными заглушками.
5. Сборка API, существующего web/demo, проверка Expo и экспорт JS/assets мобильного приложения.
   Экспорт не заменяет нативную сборку Android/iOS.
6. Регрессии существующего web/demo и API, затем согласованный сценарий 1С; мобильные E2E в подходящих runners.

Обязательные jobs не должны проходить при отсутствии ожидаемых тестов.
Если применяются фильтры путей, итоговый обязательный job корректно учитывает
пропуски и всегда сообщает результат. Полный набор выполняется для main.

PR из fork не получают секретов и не деплоятся. Не исполнять код PR через
privileged pull_request_target. permissions по умолчанию contents: read;
повышать права только конкретному job. Внешние actions закреплять полным SHA.

## Защита main

Настроить GitHub ruleset: PR, обязательные проверки, минимум один reviewer,
повторное одобрение после изменений, запрет force push и удаления ветки.
Применить ограничения к администраторам, аварийный обход регистрировать.
Проверить доступность rulesets и environments для тарифа репозитория.
Зафиксировать фактически включённые настройки; YAML не включает rulesets сам.

## После merge

- Собрать поставляемые Docker-образы API/worker и согласованного web-компонента один раз, отметить commit SHA, опубликовать
  в GHCR; получить digest, сформировать SBOM, просканировать образы.
- Связать образы, миграции, конфигурацию и мобильные сборки с commit SHA.
- Сериализовать деплои каждого окружения; не прерывать начатые миграции.
- Автоматически развернуть staging с тестовыми данными и sandbox-интеграциями.
- Выполнить readiness, API smoke и E2E заказа. Сохранять отчёты и логи без секретов.
- Не переводить релиз дальше при ошибке staging.

## Production

Использовать GitHub environment production с отдельными доступами и одобрением
ответственного. По возможности использовать OIDC и краткоживущие полномочия.
Не хранить credentials в исходниках или передаваемых артефактах.

Перед изменениями: проверить резервную копию и совместимость миграций.
Применять expand/contract; удаление старых столбцов отдельным поздним релизом.
Учитывать старые мобильные клиенты: API не ломает ранее опубликованные версии.

Продвигать тот же digest, который проверен на staging, без повторной сборки.
Выполнять rolling либо blue/green deploy в зависимости от выбранного хостинга.
После деплоя: readiness, безопасные smoke-проверки без реальных заказов,
контроль ошибок и задержек. Фиксировать версию и результат релиза.

При неуспехе вернуть предыдущий образ, если схема совместима. Не выполнять
автоматический destructive downgrade базы. При несовместимой схеме остановить
релиз и использовать проверенный план восстановления/forward fix.

## Android и iOS

- PR: JS-проверки; нативная сборка при изменении нативных зависимостей/конфигурации.
- main: development/internal build по необходимости, без автоматической публикации
  каждой правки в магазины. Контролировать стоимость EAS.
- Кандидат релиза: подписанные Android/iOS builds, тестирование на устройствах,
  TestFlight и Google Play internal testing; публикация после одобрения.
- Android/iOS builds использовать один исходный commit; окружение, bundle ID,
  версия и номера сборок фиксируются явно. Staging и production разделены.
- OTA только для совместимых JS/assets через Expo Updates с runtimeVersion,
  раздельными каналами и поэтапным распространением. Нативные изменения требуют
  новой сборки. Проверять OTA rollback на совместимую версию.
- Установленные store binaries нельзя мгновенно откатить как сервер; предусмотреть
  остановку rollout, исправляющий релиз и совместимость API.

## Регулярные проверки

Авто-PR обновлений зависимостей, ежедневный аудит, проверка резервного копирования,
периодическое восстановление в изолированном окружении. Более длительные native
E2E и проверки производительности выполнять по расписанию и перед релизом.

## Обратная связь и следующая итерация

Цикл завершается анализом релиза и возвращением результатов в план разработки.

- Связывать ошибки API, обмена 1С и мобильного приложения с release ID и commit SHA;
  загружать source maps в выбранный сервис мониторинга без публичного раскрытия.
- Наблюдать доступность API, частоту 5xx, p95 задержек, ошибки мобильного приложения,
  очередь задач, давность синхронизации 1С и сбои оформления заказов.
- До production определить численные пороги, окно наблюдения, получателей алертов
  и ответственного за инцидент. Проверить доставку тестового алерта.
- Низкий трафик учитывать отдельно: отсутствие ошибок при отсутствии запросов
  не считать доказательством здоровья релиза. Дополнить метрики synthetic checks.
- Автоматический откат выполнять только при заранее определённых условиях
  и совместимой схеме БД; остальные случаи направлять ответственному.
- Собирать отзывы пилотных пользователей и менеджеров; продуктовые события
  (поиск → карточка → корзина → заказ) не должны содержать персональных данных.
- После релиза проводить разбор показателей и отзывов. Подтверждённые дефекты
  и улучшения превращать в GitHub Issues с приоритетом, владельцем и критериями
  приёмки. Создание задач и внешние уведомления включать после настройки интеграций.
- Для инцидентов сохранять причину, действия восстановления и профилактическую
  задачу; исправление снова проходит ветку, PR, проверки и staging.
- Результат релиза: версия, проверки, миграции, решение о rollout/rollback,
  известные проблемы и задачи следующей итерации.

## Внешние подключения

1. Выбрать staging/production хостинг и домены, PostgreSQL, Redis, S3.
2. Проверить GitHub Actions, GHCR, rulesets и environment protections.
3. Подключить Expo/EAS, Apple Developer, App Store Connect и Google Play Console.
4. Настроить OIDC либо минимально необходимые credentials в защищённых settings.
5. Подключить sandbox SMS/push/1С; рабочие доступы не передавать PR jobs.
6. Выбрать мониторинг ошибок, метрик и канал уведомлений о сбоях.

Не запрашивать значения секретов в чате. Проверить существующие bindings перед
объявлением новых. Доступы для CI и runtime среды разработки — разные контексты.

## Приёмка автоматизации

- Ошибка lint, типов, тестов, миграции или утечка секрета блокирует merge.
- Внешний PR не получает production credentials.
- Успешный main разворачивается на staging и проходит функциональную проверку.
- Неуспешный staging не достигает production.
- Production требует настроенного одобрения; разворачивается проверенный digest.
- Неуспешный серверный релиз откатывается по проверенному сценарию.
- Подписанная мобильная сборка проходит internal testing; несовместимый OTA
  не доставляется клиентам.
- Новая машина воспроизводит установку; тесты и миграции выполняются с чистой БД.
- Защиты GitHub и внешние подключения проверены фактически, а не только описаны.
