# VEGA: план качества и приёмки

Актуализация: 26 октября 2026. Это требования проверки текущих инкрементов
и целевого продукта, не отчёт о готовности. Актуальные бизнес-решения —
[DECISIONS.md](DECISIONS.md); результаты конкретного среза — HANDOFF.md и CI.
Сотрудники работают в 1С, отдельная админка исключена из целевого релиза.
Существующий web/demo проверяется как стенд; он не доказывает native-готовность.

## Ответственность и цикл

Автор реализации исправляет дефект, QA независимо воспроизводит и перепроверяет.
Критик проверяет конкретные инварианты и сценарии ошибок, security — границы
доверия и реальные настройки. Проверка не заменяется обещанием «исправлено».
Backend отвечает за ACL, точные расчёты, идемпотентность и обмен; mobile —
корректный ввод, состояния и recovery; программист 1С — подтверждённые операции
в её тестовом контуре. Ни одна сторона не выдумывает возможности другой.

Задача/критерии → реализация → локальные проверки → push/PR/CI → независимый
review/retest → staging при наличии → release gate. Тестов нет или важное
поведение не согласовано — это BLOCKED, а не PASS с заглушкой.

## Критические проверки

| ID | Сценарий | Требуемый результат | Уровень |
|---|---|---|---|
| ACC-01 | Гость и зарегистрированный pending | Каталог открыт, цена/наличие отсутствуют в API, HTML/RSC, общем кэше, фильтрах и аналитике | Contract/API/browser |
| ACC-02 | Одобрение менеджером и последующий отзыв | Только approved получает разрешённые коммерческие данные; отзыв прекращает доступ и очищает приватный кэш | Integration/E2E |
| ACC-03 | Регистрация с role/approval/managerId или выбор менеджера | Сервер отвергает лишние доверенные поля; аккаунт pending, выбора менеджера в форме нет | Contract/API/browser |
| ACC-04 | Неверный пароль/неизвестный номер, перебор, expired/revoked session | Безопасный одинаковый отказ, лимиты, expiry/revoke/logout и согласованный recovery | API |
| MGR-01 | Два менеджера одновременно забирают одного свободного клиента | Один владелец, второй получает конфликт; повтор команды не меняет владельца | 1С concurrent integration |
| MGR-02 | Менеджер/клиент обращается к чужому заказу | Запрет по актуальным объектным правам независимо от UI | API/1С |
| INV-01 | Color/Color Ultima, 0/1/2 целых рулона суммарно по участвующим складам того же SKU | Все отрезы запрещены, включая готовые; при 0 запрещены и рулоны | Unit/1С integration |
| INV-02 | Color/Color Ultima, >2 целых рулонов | Порог не запрещает отрез; реальная доступность конкретного метража всё равно проверяется в 1С | Unit/1С integration |
| INV-03 | Положительный доступный остаток целых рулонов | Целый рулон разрешён независимо от порога нарезки; отсутствие SKU запрещает покупку | Unit/integration |
| INV-04 | Отрезы 1–18 м и дробный/нулевой/19 м ввод | Только целые 1–18; «Есть / Нет» соответствует отдельному метражу 1С, не сумме коротких | Unit/API/device |
| INV-05 | Другие SKU/цвета/неучаствующий склад | Не увеличивают суммарный порог текущего SKU; перечень складов задаётся согласованным контрактом | Unit/1С integration |
| INV-06 | Другие категории и длина рулона не 18 м | Color-порог не применяется автоматически; per-SKU длина не заменяется числом вариантов UI | Unit/contract |
| ORD-01 | Повтор создания после timeout/потери ответа | Один заказ и один известный результат; scoped persistent key не переносится между аккаунтами | Integration |
| ORD-02 | 1С отсутствует/устарела либо SKU/количества нет | Оформление/оплата не разрешаются по локальному кэшу; корзина сохраняется | 1С integration/E2E |
| ORD-03 | Другой канал забрал товар до списания без резерва | Согласованный отказ/изменение/компенсация; тест не обещает автоматическую защиту от перепродажи | 1С/payment concurrent integration |
| ORD-04 | Менеджер изменяет состав/цену до/после оплаты | Процесс пока OPEN: тест и реализацию утвердить до приёмки; старое обязательное повторное принятие не восстанавливать | BLOCKED до согласования |
| PAY-01 | Оплата до менеджерского согласования; частичное поступление | Нет разрешённого платежа до согласования и отгрузки до 100% подтверждённой предоплаты | Sandbox/1С |
| PAY-02 | Поддельный webhook, неверные merchant/amount/currency | Отклонение без финансового эффекта; проверенная подпись и соответствие операции | Sandbox/API |
| PAY-03 | Дубликаты, иной порядок событий, timeout и потеря return | Один финансовый факт; unknown не превращается в fail/success и не создаёт новое списание | Sandbox/integration |
| PAY-04 | Возврат повторно/конкурентно/с неизвестным исходом | Сумма успешных и pending/unknown возвратов ограничена подтверждённым поступлением; сверка и аудит | Sandbox/concurrent integration |
| PAY-05 | Сбой чека/webhook/push | Финансовый факт не теряется; есть безопасный повтор/сверка и видимое ответственному расхождение | Sandbox/integration |
| SHIP-01 | Выбор ПВЗ СДЭК на карте и смена пункта | Реальный разрешённый пункт; доставка отдельно перевозчику при получении, не нулевая «бесплатная» доставка | Provider sandbox/device |
| SHIP-02 | Создание отправления/трека в 1С | Один внешний результат, актуальный трек в нужном заказе; клиент не меняет чужую отгрузку | 1С integration |
| SYNC-01 | Повтор/старое событие/частичный снимок/удаление | Нет дубликатов или перезаписи нового старым; частичный снимок не обнуляет отсутствующие SKU | Integration |
| SYNC-02 | Обрыв обмена и восстановление | Последний успешный снимок не повреждён; явная актуальность; точный stale-порог ещё согласуется | Integration/E2E |
| MEDIA-01 | SVG, анимация, malformed/oversized file, несоответствие MIME | Безопасный отказ до опасной обработки; лимиты очереди/памяти и приватность черновиков | API/resource tests |
| NOT-01 | Push запрещён/провайдер SMS/push недоступен | Заказ/оплата сохраняются; уведомления повторяются безопасно, переход проверяет доступ | Integration/device |
| 3D-01 | Ошибка WebView, низкая память, background и смена модели | Освобождение ресурсов, безопасный fallback, каталог/корзина работают | Android/iOS device |
| REL-01 | Старый клиент и новая API/схема, rollback | Совместимость поддержанных версий, безопасные миграции и проверенный план восстановления | Contract/staging |

Правило INV-01 отменяет старое разрешение готовых отрезов при ≤2 рулонах.
Резерв ожидания оплаты и TTL не нужны по решению заказчика: не добавлять их
как скрытое условие приёмки. Повторная проверка остатка не исключает гонку
до списания; ORD-03 требует процесса, согласованного с заказчиком и программистом
1С. Без определённого поведения этот связанный коммерческий сценарий BLOCKED.
Нет тестовой 1С/провайдера — соответствующий gate не закрывается fake adapter.

## Данные, инструменты и доказательства

Текущие тесты используют закреплённый toolchain, node:test для API/contracts,
реальную PostgreSQL и Playwright для web/demo. Native E2E и устройство/runner
выбираются и проверяются отдельно; наличие Expo export не равно native E2E.
Каждому запуску — собственная схема/данные, без production credentials/получателей.
Проверять миграции с нуля и обновление поддержанной схемы; mock не доказывает
атомарность закрепления клиента или совместимость реального обмена.

Fixtures покрывают pending/approved/rejected/revoked, разные SKU/длины/склады,
0/1/2/3 рулона, готовые отрезы и отсутствие точного метража, неназначенного клиента,
два конкурирующих менеджера, недоступную 1С, unknown платёж и возврат.
Рабочие дампы, телефоны, токены и платёжные реквизиты в fixtures/артефакты не копируются.
Синтетические браузерные скриншоты не становятся настоящим каталогом заказчика.

Сохранять SHA, артефакт/build ID/digest, окружение и версии, команду, дату,
passed/failed/skipped, логи без секретов и ссылку на дефект. Результат нельзя
переносить на другой commit или пересобранный артефакт. Ретрай не скрывает
исходный сбой; обязательную нестабильную проверку расследовать и исправить.

## Gates

| Статус | Условие | Следствие |
|---|---|---|
| PASS | Все обязательные проверки конкретного scope выполнены, найденные дефекты исправлены и перепроверены | Продвижение проверенного артефакта |
| FAIL | Воспроизведён дефект/нарушение критерия | Возврат реализации владельцу, исправление и независимый retest |
| BLOCKED | Нет данных/среды/доступа либо обязательное поведение не определено | Не продвигать зависимый сценарий до устранения причины |

QA не выдаёт PASS за пустой/необъяснимо пропущенный запуск. Scope и критерии
задаются до проверки, не уменьшаются после падения. Независимые инкременты могут
продолжаться при блокере другого направления; это не разрешение коммерческого
запуска. PASS конкретного набора не обещает отсутствия всех багов.

PR gate: format/lint/types, значимые unit/integration, необходимые сборки,
secret scan и полный dependency audit. Известный HIGH node-forge сохраняется
как audit blocker, не маскируется новым job или исключением. Права GitHub,
required checks и protections проверяются фактически: YAML не включает их сам.

Staging gate: неизменяемый артефакт, миграции/readiness, реальные тестовые 1С
и платёжный sandbox, два типа покупателя, сбои/повторы, ACL после logout/отзыва.
Release gate: подписанные native builds на поддержанных устройствах, 3D/licences,
совместимость старых клиентов, restore/rollback, проверенные алерты и внешние
подключения. Реальные платежи требуют live onboarding/фискальной схемы и signoff,
не одного sandbox PASS. CI не совершает реальные списания/возвраты автоматически.

Критические утечки, неверная сумма, потерянный заказ/платёж, обход одобрения,
перепродажа и невозможность восстановления блокируют связанный выпуск.
Все дефекты текущего scope исправляются и перепроверяются; их не переносят молча
в known issues ради срока. Находка вне scope оформляется отдельно с явным
решением, влиянием и владельцем. После релиза — наблюдение, отзывы и новая итерация.

## Внешние зависимости

- Программист/тестовая база 1С обещаны; конфигурация/обмен/права ещё обследуются.
- НДС, единица цены, округление, границы stock labels, партии и stale-порог открыты.
- Процесс изменения заказа/оплаты, дефицит без резерва, дефекты/отмены/возвраты открыты.
- Эквайринг, касса и чеки отсутствуют; нужны договоры, sandbox, доверенный webhook и live signoff.
- ПВЗ СДЭК, SMS/push, мониторинг и deployment нуждаются в подключении и безопасных bindings.
- Аккаунты Apple/Google/Expo, signing, устройства, лицензированные 3D/фото/шрифты ещё нужны.
- Backup/restore требуют согласованных RPO/RTO/retention и реального восстановления.

Вход телефон+пароль не отменяет необходимость безопасного recovery/проверки номера
до production. SMS-вход позже; SMS-уведомления нужны в первом релизе.
