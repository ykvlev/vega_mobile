# VEGA: мобильное приложение

Статус: план реализации, а не описание готового приложения. Исходников мобильного
приложения пока нет; сборки, интеграции и проверки ещё не выполнялись.

## Требования и решения

Актуальные решения: [DECISIONS.md](DECISIONS.md); последовательность этапов:
[ROADMAP.md](ROADMAP.md); нормативный контракт API и recovery:
[API-CONTRACT.md](API-CONTRACT.md). При противоречии прежние предложения не
переопределяют подтверждённые решения и контракт.

Подтверждено пользователем: Android и iOS, каталог плёнок, продажа метрами и
рулонами, отдельная длина рулона у товара, личный кабинет, заказы, 3D-конфигуратор,
общая админка и API в одном репозитории. Приложение адресовано и автовладельцам,
и мастерам/студиям. Главная сочетает автомобиль, каталог и быстрый поиск по
артикулу для закупщиков. Тёмный интерфейс pushr по полученным скриншотам —
основной визуальный ориентир; присланные токены адаптируются к нему согласно
[DESIGN-BRIEF.md](DESIGN-BRIEF.md).

Гость видит каталог без цен и остатков. После входа сервер предоставляет
разрешённые коммерческие данные. Онлайн-оплата обязательна в первом рабочем
релизе: менеджер согласует заказ до оплаты; 100% предоплата предшествует отправке.
Проверенная интеграция и резервирование с 1С обязательны до реальных продаж.

Предлагаемый стек: React Native, Expo, TypeScript, Expo Router, TanStack Query,
React Hook Form и Zod. Это рабочая архитектурная рекомендация из ТЗ, а не уже
установленные зависимости. Версии закрепляются совместимым набором выбранного
Expo SDK при создании проекта; нельзя независимо брать latest каждого пакета.

Мобильное приложение отображает данные и инициирует операции. Цена, доступность,
права, резервы, назначения менеджеров и переходы статусов определяются API.

## Навигация

Предлагаемая нижняя панель: Главная / Каталог / 3D / Корзина / Профиль. Это
предложение вместо шести вкладок из обсуждения; окончательная компоновка проходит
дизайн-приёмку. Новости открываются с главной отдельным экраном.

Группы маршрутов Expo Router:

- Публичные: главная, категории, каталог, товар, новости, обучение, конфигуратор.
- Авторизация: телефон и пароль, регистрация, восстановление, завершение профиля.
- Клиентские: оформление, профиль, адреса, организация, заказы и детали заказа.
- Служебные: неизвестная ссылка, обязательное обновление при несовместимом API.

Детальные экраны открываются в stack поверх вкладки; возврат сохраняет фильтры
и положение списка. После входа пользователь продолжает начатое оформление.
Ссылки на товар/заказ проверяют существование объекта и права через API.

## Экраны и состояния

| Экран | Основные действия | Особые состояния |
| --- | --- | --- |
| Главная | Автомобиль, каталог, подбор цвета, поиск по артикулу | Обе аудитории; отказ необязательного блока не скрывает каталог |
| Каталог | Поиск, фильтры, сортировка, загрузка страниц | Нет результатов, пустая категория, ошибка следующей страницы |
| Товар | Фото, параметры, длина рулона; после входа цена и доступность | Гостевой CTA входа, архивирован, нет в наличии, нарезка запрещена, устаревшие остатки |
| Корзина | Количество, единицы, удаление, итог | Пусто, цена изменена, количество недоступно |
| Вход | Телефон и пароль, регистрация, восстановление | Неверные данные, лимит попыток, безопасное восстановление |
| Оформление | Контакты, организация, получение, комментарий | Ошибка полей, конфликт остатков, неизвестный результат запроса |
| Заказы | Список, детали, история, менеджер | Нет заказов, нет доступа, ошибка обновления |
| Условия и оплата | Принятие согласованной версии, оплата картой/счёт | На согласовании, ожидает принятия, ожидает оплаты, проверяется, оплачено, ошибка/истёк срок, требуется сверка |
| Профиль | Контакты, адреса, реквизиты, выход, удаление аккаунта | Сессия истекла, сохранение не завершено |
| 3D | Модель, цвет, вращение, переход к товару | Прогресс, нет поддержки, ошибка, статичный fallback |

Каждый сетевой экран имеет загрузку, пустое состояние, ошибку с повтором,
обновление и отсутствие сети. Кэшированные данные не маркируются актуальными
без проверки. Ошибка оформления не должна очищать корзину.

Учитываются safe areas, системная кнопка Back, клавиатура, скринридер, подписи
иконок, масштаб текста, достаточный контраст и области нажатия. Числовой ввод
учитывает запятую и точку, но отправляет нормализованное значение по контракту.

## Данные и работа без сети

- TanStack Query хранит серверное состояние; ключи включают фильтры и пользователя.
- После входа/выхода пользовательский кэш очищается или изолируется; заказы одного
  аккаунта не отображаются следующему пользователю устройства.
- Публичный каталог допускает ограниченный кэш только публичных полей. Гостевые
  ответы и общий кэш не содержат цен и остатков; скрытие значений одним UI
  недостаточно. После выхода очищается коммерческий кэш авторизованной сессии.
  Цена и доступность повторно проверяются сервером; offline checkout запрещён.
- Локальная гостевая корзина — предлагаемое решение. После входа объединяется
  с серверной по явным правилам, без молчаливого удвоения количества; цены/остатки
  для гостя не сохраняются и не выводятся. Строки адресуются по lineId, а не SKU.
  Один skuId с разными unit (метры/рулоны) — разные строки; ограничение уникальности
  серверной корзины — (cartId, skuId, unit), согласно API-CONTRACT.md.
- Источником итога служит ответ API с точной денежной арифметикой; UI не вычисляет
  финансово значимые результаты числами floating point самостоятельно. Money —
  `{amountMinor: "125000", currency: "RUB"}`: целые минимальные единицы строкой,
  валюта примера не определяет production. Длина — целые миллиметры строкой;
  отображаемые метры преобразуются точно, дробных метров в DTO нет.
- Количество позиции вложенное: `quantity: {lengthMm: "5000"}` для meter,
  `quantity: {count: 1}` для roll/piece. Upsert устанавливает абсолютное количество
  с expectedCartVersion; обновление по lineId использует expectedLineVersion.
- Не сохранять токены, реквизиты и персональные данные в обычном persisted query
  cache. Объём и срок хранения локальных данных определить при реализации.

## Авторизация

Подтверждённый первый способ входа — телефон и пароль. SMS-вход добавляется
позже и не блокирует bootstrap. Безопасное восстановление доступа определить
до использования рабочих аккаунтов; клиент не обещает несуществующий канал.

Сервер ограничивает попытки входа. Пароль и токены не попадают в логи,
аналитику и URL. Сессию хранить в SecureStore; детали access/refresh и ротации
зафиксировать в контракте API. Обновление сессии сериализовать, чтобы параллельные
401 не запускали множество refresh-запросов. При окончательном отказе предложить
вход, сохранив безопасный контекст оформления. Выход отзывает сессию на сервере.

Тестовый вход возможен только в изолированном окружении. Универсального пароля
и обхода проверки в production быть не должно.

## Каталог, метры и рулоны

Карточка показывает артикул, характеристики, ширину, длину полного рулона,
фото и описание. Цены с единицами и доступность доступны только после входа.
Аксессуары используют собственные единицы продажи. Цена доставки не изображается
рассчитанной, если её ещё нет.

Доступные способы продажи, минимум, шаг и порог нарезки возвращает API.
Подтверждённое правило: при двух полных рулонах и меньше новая нарезка из целых
рулонов запрещена, но готовые отрезы продавать можно при достаточной длине.
Приложение не должно
самостоятельно выводить число целых рулонов делением общего метража.

Количество валидируется в UI для удобства и повторно на сервере. Сообщение
о запрете объясняет причину и доступную альтернативу — полный рулон, если доступен.
Цветовой образец сопровождается пояснением о приблизительной передаче экраном.

## Оформление и заказы

Последовательность: вход → контакты/организация → получение → отправка заказа
на согласование только после успешных quote/submit с проверкой актуальной 1С
→ менеджер фиксирует окончательные состав, цену и условия доставки
→ клиент принимает эту версию → сервер проверяет актуальную доступность и резерв
1С → оплата картой либо по счёту → сервер подтверждает 100% предоплату → разрешена
отправка. Онлайн-оплата входит в первый рабочий релиз. Отправка несогласованной
корзины не создаёт права на немедленную оплату или гарантированное наличие.

- Добавление в корзину не резервирует склад.
- Production quote и submit при отсутствующем SKU/недостатке получают
  STOCK_UNAVAILABLE, при stale/unavailable — INVENTORY_CONFIRMATION_UNAVAILABLE.
  Order не создаётся, корзина сохраняется; нельзя показывать «заявка принята».
  Проверка при submit не резервирует товар: перед оплатой проверка и резерв 1С
  обязательны повторно.
- До первого запроса сохранить Idempotency-Key и неизменяемый payload операции
  в приватном persistent-хранилище текущего аккаунта. При timeout, перезапуске
  или неизвестном результате повторять исходный POST с тем же ключом и телом.
  Отдельный lookup endpoint не предполагается. REQUEST_IN_PROGRESS обрабатывается
  с Retry-After и повтором того же POST; новый payload под тем же ключом даёт
  409 IDEMPOTENCY_CONFLICT. Retention и истечение ключа — по API-CONTRACT.md;
  нельзя молча генерировать новый ключ для неопределённой старой операции.
- Ключ/контекст pending-операции не переносить между аккаунтами. Сохранённый payload
  может содержать персональные данные: ограничить доступ, срок хранения и очистку
  по протоколу, не класть его в общедоступный query cache. Отключение кнопки не
  заменяет идемпотентность и восстановление операции.
- При конфликте показать изменённые позиции и получить повторное подтверждение.
- API обеспечивает согласованность заказа и резервов по проверенному протоколу
  1С; локальная транзакция сама по себе не резервирует остатки других каналов.
  Если SKU отсутствует в 1С, остатка недостаточно, 1С недоступна или данные
  устарели, автоматическая оплата/подтверждённая покупка блокируются сервером.
- Детали содержат снимок состава/цен заказа, отдельное состояние оплаты,
  историю исполнения и назначенного менеджера.
- Менеджерское approval/изменение статуса используют expectedOrderVersion;
  клиент принимает точные orderVersion/deliveryVersion, а payment attempt содержит
  также paymentTermsVersion. Изменившаяся версия требует актуальных условий,
  не автоматического повторного согласия клиента.
- Возможность самостоятельной отмены и допустимые статусы согласуются отдельно.

Оплата выполняется по принятой версии заказа. Изменение суммы/состава/условий
требует нового согласования; старый платёжный запрос не должен оплатить другую
версию. Redirect/deep link и скриншот не подтверждают поступление денег: приложение
запрашивает серверное состояние. Обрабатываются незавершённый checkout, отмена,
повторное открытие приложения и поздний платёж после истечения резерва; последний
показывается как сверка/обработка по правилам API, без обещания отправки.

Доставка: Россия — СДЭК/Деловые Линии, Москва — Яндекс Доставка, МО — СДЭК/такси;
самовывоз — Москва, Бережковская набережная, д. 38, стр. 2. Формы собирают
соответствующие контакты/адрес или ПВЗ. Автоматические API перевозчиков не обещаны;
окончательные стоимость и порядок оплаты доставки согласуются до платежа.

## 3D и WebView

Three.js внутри react-native-webview — кандидат реализации, который сначала
проверяется на реальных устройствах обеих платформ. Expo Go не является
достаточным доказательством готовности production build.

Прототип должен проверить WebGL, память при смене моделей, восстановление
после background/foreground, нагрев, жесты, низкую память и сетевые ошибки.
Целевые устройства, ограничения размера GLB/текстур и численные бюджеты FPS/памяти
устанавливаются по результату прототипа до наполнения каталога моделями.

Требования к границе WebView:

- Сцена получает только проверенные model/material IDs и разрешённые ресурсы.
- Сообщения JS bridge имеют версию и проверяемую схему; произвольный код
  из API или пользовательского ввода не выполняется.
- Навигация ограничена разрешёнными origin; внешние страницы не получают bridge.
- Токены пользователя не передаются сцене. Загрузка приватных ресурсов, если
  нужна, проектируется отдельным ограниченным механизмом.
- При смене модели освобождаются geometry/material/texture и WebGL resources.
- Пакет сцены версионируется вместе с приложением или через совместимый OTA;
  произвольный удалённый HTML не используется как скрытое обновление приложения.

Кузов меняет материал, стёкла/колёса/салон сохраняются. VEGA присутствует на
номерных знаках. Нужны лицензированные модели и материалы; наличие моделей
конкретных марок пока не подтверждено. 3D не блокирует каталог и checkout.

## Сборки и доставка

Согласовать стабильные application IDs и разделить development, staging и
production. API URL — публичная конфигурация, а не секрет; секреты нельзя
включать в EXPO_PUBLIC_* или bundle. Изображения/GLB не раздувают начальный bundle.

- Development build проверяет реальные native modules.
- Android: эмулятор для автоматизации и реальные устройства перед выпуском.
- iOS: macOS runner/Xcode либо EAS; реальные устройства и TestFlight.
- Expo export проверяет JS/assets, но не заменяет компиляцию native-кода.
- Подписанные release builds создаются из известного commit SHA.
- OTA использует runtimeVersion и отдельные каналы; новые native зависимости
  требуют новой сборки. Store policies учитываются при выборе обновлений.
- Установленную бинарную версию нельзя мгновенно откатить серверным rollback;
  нужны остановка rollout, совместимый API и исправляющий выпуск.

Общий цикл описан в CI-CD.md. Аккаунты Expo/Apple/Google, signing и deployment
ещё не подключены. Сборки и публикация не считаются выполненными по наличию YAML.

## Первый вертикальный сценарий

1. Использовать API-CONTRACT.md для товара, единиц, ошибок, корзины и recovery.
2. Ввести небольшой тестовый набор: рулон с доступной нарезкой, товар на пороге,
   отсутствующий товар. Все данные явно демонстрационные.
3. Реализовать каталог → карточку → гостевую корзину на реальном API.
4. Подключить телефон/пароль в staging и профиль минимального состава.
5. Реализовать проверку заказа, идемпотентное создание и экран результата.
6. Проверить появление того же заказа у менеджера в админке и обновление статуса
   в приложении. Это завершает первый сквозной сценарий, а не только макет UI.
7. Дальше по ROADMAP.md: подтверждённая 1С → согласование менеджером и принятие
   версии клиентом → sandbox онлайн-оплаты/счёта → серверная проверка предоплаты
   → разрешение отправки. До этого сквозной заказ — только демонстрационный.
8. Развивать главную, контент, расширение профиля и 3D; 3D-прототип и обследование
   1С проводить заранее независимо от наполнения этих экранов.

## Критерии приёмки мобильного направления

- На Android и iOS клиент проходит сценарий от каталога до номера заказа;
  админка отображает тот же заказ и его назначенного менеджера.
- При двух полных рулонах и меньше запрещена новая нарезка; доступные готовые
  отрезы продаются. Серверный отказ корректно отображается при устаревшем кэше.
- Гостевой API и общий кэш не содержат цен/остатков; после выхода закрытые данные
  не остаются в UI, поиске или пользовательском кэше.
- Изменившиеся цены/остатки требуют подтверждения; timeout и повтор не дублируют
  заказ, корзина не теряется при ошибке.
- Каталог остаётся доступен при ошибке новости или 3D; отсутствие сети имеет
  явное состояние и безопасный повтор.
- Выход/смена пользователя не раскрывают прежние заказы и реквизиты.
- Перезапуск после timeout восстанавливает тот же POST/key/payload. Разные unit
  одного SKU адресуются разными lineId; конфликт ключа не создаёт новый заказ.
- До менеджерского согласования и принятия версии кнопка оплаты недоступна;
  сервер также запрещает её. Нет 1С/доступности/резерва — нет автоматической оплаты.
- Нет актуальной 1С, SKU или достаточного остатка уже на quote/submit — Order
  не создаётся и UI сохраняет корзину. После успешного submit перед оплатой снова
  проверяются 1С и общий резерв; локальный кэш этого не заменяет.
- Redirect не меняет заказ на оплаченный; отправка разрешается только после
  серверного подтверждения 100% предоплаты. Sandbox проверяет позднюю оплату,
  возврат/сверку и обновление согласованной версии.
- Push без разрешения пользователя не мешает основному сценарию; разрешённый
  переход проверяет права и открывает актуальные данные заказа.
- Нативные release builds проходят проверку на согласованных устройствах;
  JS export и нулевой запуск тестов не считаются приёмкой.
- До заявлений о готовности 3D подтверждены совместимость, лицензии и измеренные
  бюджеты; отсутствие материалов отражается как отдельный блокер.

## Зависимости и открытые вопросы

Нужны реализация согласованного API-контракта, staging авторизации телефон/пароль,
безопасное восстановление, тестовые товары/фото, правила отмены и сроки резервов,
целевые ОС/устройства, лицензированные шрифты и 3D-модели. Детали оплаты доставки,
эквайринг и фискализация ещё согласуются. Наличие staging, аккаунтов stores,
push credentials и рабочего обмена 1С не подтверждено; SMS не prerequisite.
Эти внешние зависимости не мешают подготовить основу и тестовый сквозной сценарий,
но ограничивают production и соответствующие проверки.
