# VEGA: мобильное приложение

Актуализация: 29 октября 2026. Целевой план iOS/Android и текущий срез.
В apps/mobile реализован React Native клиент: каталог, карточка, локальный подбор,
вход и профиль с одобрением. Подробности и запуск — [MOBILE-CUSTOMER.md](MOBILE-CUSTOMER.md).
JS-компиляция и browser-проверки не заменяют приёмку на телефонах или рабочие продажи.
[DECISIONS.md](DECISIONS.md), [решения встречи](CUSTOMER-MEETING-2026-10-26.md)
и уточнения пользователя имеют приоритет. Контракт обмена с реальной 1С ещё
требует обследования; обещанные программист и тестовая база пока не получены.

## Продукт и границы

Приложение для автовладельцев и мастеров: автомобиль, каталог, быстрый поиск,
карточки плёнки с отдельной длиной рулона, подбор цвета, корзина, заказы,
профиль, новости/обучение и 3D. Весь согласованный первый релиз сохраняется;
порядок инкрементов не исключает функции из запуска. Текущий визуальный ориентир — LIMÉ: белые внутренние экраны,
автомобильная фотография на главной; брендбук ещё ожидается. Логотип используется с дескриптором.

Отдельной админки VEGA в целевом продукте нет. Сотрудники обслуживают клиентов,
товары, заказы и отгрузки через 1С. Desktop demo остаётся техническим стендом.
Backend VEGA защищает доступ и связывает mobile с 1С, оплатой и уведомлениями;
клиент не обращается напрямую к БД или 1С и не получает их секреты.

Текущий стек bootstrap: React Native/Expo/TypeScript; дополнительные библиотеки
навигации, форм, серверного кэша и E2E вводятся после проверки совместимости.
Версии берутся из lockfile, не из произвольных latest. Сборка JS export не
заменяет компиляцию и проверку Android/iOS на устройствах.

## Доступ и менеджеры

| Состояние | Каталог/характеристики | Цены и наличие | Следующий шаг |
|---|---|---|---|
| Гость | Да | Нет | Вход или регистрация |
| Зарегистрирован, ожидает одобрения | Да | Нет | Проверка менеджером |
| Одобрен менеджером | Да | Только разрешённые API данные | Проверка доступности перед заказом |
| Одобрение отклонено/отозвано | Да | Нет | Обращение к менеджеру |

Регистрация не равна одобрению и не подтверждает связь с контрагентом.
Менеджера покупатель не выбирает: поля выбора нет. Менеджер сам забирает
свободного клиента; конкурентное закрепление должно дать одного владельца.
Источник назначения и операции 1С согласуются с её программистом. Клиентский
payload не может назначить менеджера, повысить роль или одобрить себе доступ.

Первый вход — телефон и пароль; SMS-вход позже. SMS и push уведомления нужны
в первом релизе и не означают SMS-вход. Подтверждение владения номером и безопасный
recovery определить до production. Пароли/токены не попадают в URL, аналитику
и логи; сессии в native SecureStore, browser cookie HttpOnly/Secure.
Выход отзывает сессию и очищает приватный кэш, отзыв одобрения закрывает данные
при следующей серверной проверке. Нельзя доверять сохранённому клиентскому флагу.

## Навигация и состояния

Предлагаемые вкладки: Главная / Каталог / 3D / Корзина / Профиль.
Экран новости/обучения открывается с главной; детали в stack сохраняют контекст.
Web demo `/` открывает клиентскую концепцию, а не рабочее место сотрудника.

| Экран | Информация и действия |
|---|---|
| Главная | Автомобиль, категории, быстрый поиск по артикулу, контент |
| Каталог | Фильтры, пагинация, карточки; коммерческий доступ только после одобрения |
| Товар | Фото, артикул, характеристики, длина рулона per-SKU, метраж/рулоны |
| Корзина | Позиции, единицы, серверный итог после одобрения; причина недоступности |
| Регистрация | Телефон/пароль, без выбора менеджера; объяснение ожидания одобрения |
| Профиль | Состояние доступа, контакт закреплённого менеджера после назначения |
| Оформление | Получатель/контакты, ПВЗ СДЭК на карте, иной согласованный способ получения |
| Заказ | Номер, состав, отдельные финансовое и исполнительское состояния из API/1С |
| Оплата | Серверный статус, карта/счёт; unknown не равен отказу или успеху |
| 3D | Модель, материал, вращение, товар и безопасный fallback |

Все сетевые экраны имеют загрузку, пустое состояние, ошибку с повтором,
отсутствие сети и явную давность кэша. Ошибка запроса не выглядит пустым списком,
ошибка оформления не стирает корзину. Учитывать safe areas, клавиатуру,
системный Back, скринридер, крупный текст, контраст и доступный размер целей.

## Карточка, метраж и склад

- Длина рулона задаётся для конкретного товара; варианты 1–18 м не означают,
  что каждый рулон имеет длину 18 м. Учёт ширины в 1С пока не подтверждён.
- Метраж — плитки целых значений 1–18 м с шагом 1 м. Для одобренного клиента
  наличие каждого метража — «Есть / Нет» по данным отдельных отрезов 1С.
  Гость/ожидающий одобрения не получает эти признаки даже через скрытый DTO.
- Для Color/Color Ultima при суммарном остатке ≤2 целых рулонов соответствующего
  SKU по участвующим складам запрещены ВСЕ отрезы, включая готовые. Нельзя
  обойти запрет покупкой ранее учтённого отреза. Правило проверяет сервер.
- Целый рулон можно купить при любом положительном доступном остатке. Нулевой
  остаток не разрешает покупку. Для других категорий порог не придумывается.
- Не выводить число рулонов или непрерывный отрез из общей суммы метров.
  Несколько коротких отрезов не доказывают наличие одного длинного.
- Состав складов, партии/разнотон, цены и округление ещё согласуются.
  Границы «много / достаточно / мало» не реализовывать с пересечениями;
  нельзя объявлять «мало» при нуле так, чтобы покупка оставалась доступна.
- UI показывает причины запрета и доступную альтернативу — рулон, если есть.
  Цвет на экране условный, нужен физический образец для точного выбора.

## Данные, кэш и обмен

Публичная проекция содержит только публичные поля. Приватный кэш изолируется
по аккаунту и состоянию одобрения, очищается при выходе/отзыве доступа. Ни цена,
ни наличие не попадают в общий кэш, HTML, фильтры, сортировки, дикторские подписи
или аналитику гостя/неодобренного клиента. Цена и доступность считаются сервером.

Money хранит целые минимальные единицы строкой; длины — целые миллиметры, количество
рулонов — целое положительное число. Финансовые значения не вычисляются через
binary float в UI. Конкретные DTO заказа/корзины ещё согласуются с API и 1С;
не выдавать старые endpoint/версионные поля за реализованный контракт.

Предложение для сбоя обмена: показывать последний успешный снимок каталога
с явной актуальностью и блокировать оформление/оплату при stale/unavailable.
Порог свежести и возвращение в online ещё утверждаются. Offline checkout
не допускается. Известный снимок не означает гарантированного наличия.

## Заказ, оплата и доставка

Целевой процесс: заказ в 1С → менеджер согласует условия → 100% предоплата
картой или по счёту → доверенное серверное подтверждение → отгрузка в 1С.
Менеджер вправе изменить состав/цену. Отдельное повторное принятие клиентом
ранее исключено, но последним ответом весь процесс изменений оставлен открытым:
показ актуального итога, контроль версии платежа, доплата/возврат до реализации
ещё согласуются. Не вводить обязательный acceptance endpoint по старому ТЗ.

Резерв на время ожидания оплаты исключён. Не вводить скрытый резерв в backend.
Проверка актуальной 1С перед оформлением и оплатой всё равно нужна. Она не
защищает промежуток до списания от конкурирующего канала: согласовать отказ,
изменение заказа и компенсацию. Не обещать гарантированный товар без такого
процесса и не маскировать отказ принятой заявкой.

Создание заказа и платёж требуют scoped persistent idempotency и восстановления
неизвестного исхода. При timeout повторять согласованную операцию с прежним
ключом и телом, не создавать новый заказ/платёж вслепую. Ключ и приватный контекст
не переносить между аккаунтами. Формат и retention определяются новым контрактом.
Redirect/deep link, PDF счёта и скриншот не доказывают поступление. Платёжный
статус приходит с backend по доверенному webhook/серверной сверке; частичная
оплата не разрешает отгрузку. Платёж нельзя переписать на иную сумму молча.
Эквайринг, онлайн-касса и сервис чеков ещё не подключены.

Доставка оплачивается отдельно перевозчику при получении, не входит в оплату
товаров. Выбор ПВЗ СДЭК на карте обязателен в первом релизе. Отправление и трек
создаёт 1С. Для других названных служб/регионов согласовать формы и API. Адрес
и часы самовывоза перепроверить: прежний адрес поставлен под сомнение. Возврат
нарезки заказчик исключил, но дефекты, недопоставка, отмены и возвраты денег
нуждаются в отдельном согласованном процессе.

SMS/push уведомления не влияют на факт заказа/оплаты. Отказ пользователя от push
не блокирует приложение; переход проверяет сессию, объектные права и актуальные
данные. Уведомление не должно раскрывать лишние коммерческие/персональные данные.

## 3D, ресурсы и native-поставка

Реализован браузерный Three.js-стенд: [3D-CONFIGURATOR.md](3D-CONFIGURATOR.md).
Встраивание через WebView остаётся кандидатом; решение проверяется на реальных
Android/iOS до массового наполнения. Expo Go или web preview не доказывают готовность.
Проверить WebGL, память/нагрев, background/foreground, низкую память, смену моделей,
освобождение geometry/material/texture и безопасный статичный fallback.
Лицензии моделей/шрифтов/фото подтверждаются до поставки; контент — оператор,
исходники фото — фотограф, дизайн принимает Сергей Фёдорович.

Bridge имеет версию и строгую схему, принимает только известные model/material IDs.
Не исполнять код из API, не передавать токены в сцену, ограничить navigation/URI
allowlist, запретить произвольные внешние URI моделей. Стёкла/колёса/салон не
перекрашиваются вместе с кузовом; VEGA на номерных знаках по дизайн-приёмке.
Размеры GLB/текстур и бюджеты памяти/FPS устанавливаются измерениями на целевых
устройствах. Ошибка 3D не блокирует каталог или корзину.

Development, staging и production разделены; API URL не секрет, но ключи нельзя
включать в EXPO_PUBLIC_* или bundle. Подписанные builds связаны с commit SHA;
iOS требует Xcode/macOS либо EAS, TestFlight и реальные устройства, Android —
internal testing и реальные устройства. OTA только совместимые JS/assets по
runtimeVersion и каналам; native-изменения требуют новой бинарной сборки.
Серверный rollback не откатывает мгновенно уже установленные store binaries.
Аккаунты, signing и магазины ещё не подключены; даты не гарантированы.

## Приёмка и следующий инкремент

1. Подтвердить контракт и read-only обмен 1С; сверить карточки, фото, длины,
   отрезы, цены и состояние одобрения в тестовой базе.
2. Проверить гостя, pending, approved, rejected/revoked; приватные данные не
   сохраняются после выхода/отзыва и не доступны прямым запросом.
3. Проверить Color/Color Ultima при 0/1/2/3 рулонах, готовые отрезы, суммарные
   склады, недоступный метраж и иной SKU; UI не обходит серверный запрет.
4. Проверить закрепление свободного клиента двумя менеджерами: один владелец.
5. После согласования изменений заказа пройти заказ в тестовой 1С и sandbox
   платежа, повторы/timeout, конкурентную продажу без резерва и восстановление.
6. Проверить ПВЗ/доставку/трек, SMS/push, дефекты/отмены/возвраты по утверждённым правилам.
7. Пройти связанные сценарии и ошибки на подписанных Android/iOS builds,
   доступность, разные экраны/текст, совместимость старого клиента и 3D-бюджеты.

Каждая поставка проходит CI и QA по конкретному SHA/артефакту. Fake adapter
и web demo не заменяют приёмку настоящей 1С, native builds или live-платежей.
