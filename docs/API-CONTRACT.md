# VEGA — API и границы контрактов

Актуально на 26 октября 2026. Бизнес-правила: [DECISIONS.md](DECISIONS.md),
открытые решения: [встреча](CUSTOMER-MEETING-2026-10-26.md).
Этот документ отличает действующий demo API от ещё не согласованного интерфейса
1С и будущих продаж. Старый контракт с резервом/TTL, отдельной админкой и
обязательным повторным принятием менеджерских изменений отменён.

## Действующий demo API

REST `/api/v1`, JSON, идентификаторы UUID. Точные схемы и ограничения находятся
в `packages/contracts/src`, реализация — `apps/api/src`. При расхождении описания
с кодом нельзя объявлять новый endpoint работающим только по этому документу.

| Endpoint | Реализованное поведение |
|---|---|
| GET /health/live, /health/ready | Живость/готовность, demo mode, commerceEnabled=false; готовность проверяет БД |
| GET /api/v1/categories | Публичные категории, cursor/limit |
| GET /api/v1/products | Только опубликованные карточки; q/categoryId/cursor/limit, буквальный поиск без wildcard-инъекции |
| GET /api/v1/products/:id | Публичная карточка опубликованного товара, иначе безопасный 404 |
| POST /api/v1/auth/register | Строго `{phone,password}`, создаётся customer; роль, одобрение и менеджер не задаются покупателем |
| POST /api/v1/auth/login | Телефон + пароль, одинаковая безопасная ошибка неверных учётных данных |
| GET /api/v1/me | Профиль текущего владельца серверной сессии |
| POST /api/v1/auth/logout | Отзыв сессии, 204; нельзя считать logout успешным при недоступном API |
| GET /api/v1/media/:id | Нормализованное WebP; посетителю только опубликованный товар, сотруднику demo доступны его закрытые операции |

Auth включается только в изолированном demo, защищён rate limits и bounded KDF.
Регистрация не подтверждает номер и не открывает коммерческие данные.
Профиль содержит `commercialAccessStatus: pending|approved|rejected|revoked`,
регистрация принудительно задаёт pending. Login/me возвращают текущее состояние
из БД; роль сотрудника и одобрение клиента — разные признаки. Одобрение должно
приходить из согласованного процесса 1С. Публичного endpoint самостоятельного одобрения нет.
Текущий demo не содержит работающих offers, корзины, заказов или платежей.

Существующий `/api/v1/admin/*` и desktop-редактор — сохранённый тестовый стенд
прошлых срезов, не часть целевого продукта и не путь сотрудников в production.
Описание его тестов не означает готовую интеграцию управления через 1С.

## Доступ и сериализация

Гость и клиент без одобрения видят только публичную проекцию: ID, артикул,
название, категорию, описание/характеристики, фото и размеры. Цена, наличие,
свежесть закрытого складского снимка и доступность метражей в этих ответах
отсутствуют целиком. Не допускаются утечки через HTML/RSC, JSON-LD, shared cache,
поисковые агрегаты, ошибки или browser storage. Цены не становятся публичными
при входе, выборе типа клиента или закреплении менеджера без одобрения.

Приватные ответы требуют текущей серверной сессии и проверки одобрения/прав;
`Cache-Control: private, no-store`. Отзыв одобрения закрывает последующие запросы,
а не только следующий вход. Пользователь не может передать своё решение об
одобрении или назначении менеджера в регистрации/изменении профиля.

Web хранит сессию в Secure/HttpOnly host-cookie и проверяет Origin для мутаций;
mobile должен использовать защищённое хранилище. Секреты API/1С и банковские
данные не включаются в DTO. Cookie/bearer не экспортируются в клиентский кэш.

## Будущий контракт коммерческих операций

Это требования к проектированию, не реализованные endpoints. Их маршруты,
поля, статусы и ошибки фиксируются после обследования 1С, а затем проверяются
контрактными тестами. Нельзя использовать старую таблицу cart/quote/reserve/accept
как готовый контракт нового процесса.

- Предложение товара доступно только одобренному клиенту и содержит серверную
  цену, разрешённые единицы/метражи, версию и состояние актуальности 1С.
- Плитки 1–18 м имеют шаг 1 м; «Есть / Нет» зависит от конкретных отрезов 1С,
  а не суммы несвязанных длин. Длина рулона остаётся характеристикой SKU.
- Для Color/Color Ultima при суммарном остатке ≤2 целых рулонов соответствующего
  SKU по участвующим складам запрещены ВСЕ отрезы, включая готовые. Целый рулон
  разрешён при достаточном положительном наличии. Другие SKU не суммируются.
- Нельзя оформить или оплатить отсутствующий/недостаточный товар. Нужна повторная
  серверная проверка 1С; локальная копия не гарантирует наличие. Резерв ожидания
  оплаты исключён, скрытый резерв VEGA не вводится. Гонка с другими каналами
  остаётся открытым вопросом процесса и компенсаций.
- Заказы поступают в 1С и обрабатываются менеджером там. Поступление в очередь
  обмена не равно подтверждённому созданию в 1С. Повтор после неизвестного исхода
  сверяется по устойчивому внешнему ID и не создаёт второй заказ.
- Покупатель не выбирает менеджера. Менеджер забирает свободного клиента;
  конкурентное закрепление допускает одного владельца. Операцию и источник
  назначения согласовываем с программистом 1С, не выдумываем публичный staff API.
- Менеджер меняет состав/цену. Отдельное повторное принятие ранее исключено,
  но весь процесс изменений, показ итога и финансовые последствия пока открыт.
  Не реализовывать обязательный acceptance endpoint или молчаливую смену суммы
  существующей платёжной попытки до принятия нового контракта.
- Доставка отдельно перевозчику при получении. ПВЗ СДЭК выбирается на карте,
  отправление и трек создаются в 1С. Контракт ПВЗ/адреса/треков ещё требуется.

## Точность, повторы и восстановление

Суммы передаются целыми минимальными единицами со строго заданной валютой;
длина — целыми базовыми единицами, количество рулонов — целое. Точный формат
DTO, НДС, единица цены и округление согласуются по реальным примерам 1С.
Binary float не используется для денег. «Округлить в плюс» само по себе не
определяет точность или этап округления.

Для будущих мутаций нужен устойчивый идемпотентный идентификатор, привязанный
к владельцу и нормализованному содержимому запроса. Повтор того же действия
восстанавливает его результат; тот же ключ с другим содержимым отвергается.
Клиент сохраняет идентификатор до запроса, чтобы сетевой timeout не создавал
новый заказ/списание. Конкретные сроки хранения и recovery API ещё согласуются.

Обмен использует версии, checkpoint, различение полного/частичного снимка,
проверяемые подтверждения и сверку неизвестного исхода. Неполный или ошибочный
снимок не обнуляет каталог. Старое событие не перезаписывает новое.
Ошибки клиента не раскрывают SQL, внутренние адреса, токены и стек.
При stale/unavailable предлагается оставить просмотр последнего каталога,
блокируя оформление/оплату; точный порог свежести требует согласования.

## Приёмка нового контракта

Проверить ACL гостя/ожидающего/одобренного/отозванного клиента; пороги 0/1/2/3
рулона и готовые отрезы; идемпотентный заказ в тестовую 1С; двойное закрепление
клиента; stale/обрыв/перезапуск обмена; потерю ответа и неупорядоченность событий.
Платёжные подписи, сумма/валюта, повторы webhook, возвраты и сверка — PAYMENTS.md.
Fake adapter не заменяет приёмку на тестовой базе заказчика.
