# VEGA: план разработки

Статус: bootstrap приложений и GitHub CI реализованы в draft-ветках. Есть независимый
дизайн-прототип и гостевой каталог из PostgreSQL; их удалённые browser jobs
прошли (PR4, run40185961310). Следующий независимый срез — серверная
авторизация в изолированном demo-режиме. Этап 1 остаётся
BLOCKED из-за HIGH-уязвимости node-forge; production и native-релиз не допущены.
Брендбук ожидается; временная тема позволяет продолжать независимые задачи.
План не означает выполненную реализацию. Сроки оцениваются по завершённым этапам
и после проверки 1С, 3D и платёжных условий, а не по числу созданных агентов.

## Общий цикл каждого этапа

Задача и критерии → ветка → реализация → локальные проверки → push/PR →
обязательный CI → независимые QA/security/review → merge → staging при наличии
развёртываемого приложения → smoke/E2E → итог этапа и следующие задачи.

FAIL/BLOCKED не продвигается по зависимой цепочке. Не создавать фиктивные
проходящие jobs вместо ещё не реализованных тестов. Документация не требует
деплоя; JS export не заменяет native build. Production и магазины не обновляются
на каждом этапе: выпуск идёт после полного допуска. GitHub checks должны быть
фактически настроены, а не только описаны в YAML.

| Этап | Где и что делаем | Проверяемый результат |
|---|---|---|
| 0. Согласованная основа | docs: решения, scope, API-контракты, прототип правил заказа/оплаты | Закрыты противоречия, выделены внешние зависимости; неизвестное не выдано за готовое |
| 1. Bootstrap и CI | Корень, apps/mobile, apps/admin, apps/api, packages, infrastructure, .github/workflows | Закреплённые инструменты, установка по lockfile, запуск с чистой БД, API readiness, реальные сборки и первый содержательный тест; GitHub push/PR run при доступности удалённой ветки |
| 2. UI-основа | packages/design-tokens, mobile, admin | Тёмная тема pushr, навигация, адаптация кириллицы, состояния загрузки/ошибки; первый макет главной и каталога на тестовых данных |
| 3. Товары и доступ | API/Prisma, admin, mobile | Сотрудник создаёт товар/фото/длину рулона, гость видит каталог без цен/остатков, клиент после входа видит разрешённые данные; проверка ACL и кэша |
| 4. Корзина и локальный заказ | API, mobile, admin | Метры/рулоны, пересчёт, точность, идемпотентность, конкурентные резервы, распределение менеджеров, подтверждение условий; только демонстрационные продажи |
| 5. Обмен с 1С | API integration adapter, worker, admin | Реальный тестовый обмен и резерв по согласованному протоколу; отсутствие SKU/остатка, сбои и конкурирующие каналы закрывают возможность заказа/оплаты |
| 6. Оплата и доставка | API payments, mobile checkout, admin | Менеджер согласует заказ → выставлены окончательные условия → 100% предоплата картой или по счёту → серверное подтверждение → разрешена отправка; sandbox webhook/refund/race E2E |
| 7. 3D | packages/configurator, mobile, файловое хранилище | Лицензированные модели, кузов/материалы, VEGA на номерах, связь с товаром, fallback; измерения на Android/iOS |
| 8. Контент и сервис | admin/API/mobile | Новости, обучение, уведомления и профиль; публикации и заявки проходят сквозные проверки |
| 9. Пилот и усиление | Все приложения и staging | Пользовательские сценарии, устройства, native builds, perf/security, restore/rollback, старые API-клиенты; все дефекты текущего scope исправлены и перепроверены |
| 10. Выпуск | Production, EAS, TestFlight/Play, мониторинг | Тот же проверенный артефакт, миграции, одобрение релиза, smoke, алерты, инструкции; публикация магазинами отдельный внешний шаг |
| 11. Следующая итерация | Мониторинг, отзывы, backlog | Разбор релиза, подтверждённые дефекты/метрики → новые задачи с критериями приёмки |

Ранние технические исследования 1С и 3D выполняются параллельно bootstrap:
не откладывать обнаружение невозможного обмена или неподходящих моделей до этапов 5/7.
Security и QA участвуют с первого этапа; маркетинг и UX проверяют сценарии до UI.
Первую демонстрацию можно сделать после этапа 3, сквозной тестовый заказ — после 4.
Реальные деньги и продажи запрещены до подтверждённых 1С и payment readiness.

## Поставка и счета

Источник: условия VEGA, переданные пользователем. Менеджер подтверждает заказ,
согласует условия и предоставляет данные оплаты. Предоплата 100%; отправка после
подтверждения поступления средств. Онлайн-оплата первого релиза добавляется после
согласования, а не подменяет менеджерский шаг. До платежа наличие/резерв
проверяются повторно; срок ожидания оплаты должен быть согласован с TTL резерва.
После изменения суммы/состава старый платёжный запрос не должен оплатить неверную версию.

- Россия: СДЭК и Деловые Линии, доставка за счёт клиента.
- Москва: Яндекс Доставка, нужны телефон и адрес.
- Московская область: СДЭК или такси.
- Самовывоз: Москва, Бережковская набережная, д. 38, стр. 2.
- Для ПВЗ: выбранный перевозчик/пункт, имя и телефон получателя.
- Карты и счета юрлиц: разные процессы подтверждения оплаты; скриншот клиента
  не служит доказательством поступления. Зафиксировать источник проверки по счёту.

Провайдер, фискализация, порядок оплаты стоимости доставки и сроки оплаты/резерва
требуют уточнения. Автоматические API перевозчиков не следуют из перечисления
служб: первый релиз допускает согласование и оформление доставки менеджером.

## Итог каждого этапа

Сообщать пользователю: что изменено, где смотреть результат, какие проверки
реально выполнены, PASS/FAIL/BLOCKED, обнаруженные дефекты, внешние блокеры
и следующий этап. Ссылки на commit/PR/CI/deploy указывать только если они существуют.

## Передача контекста

Обновлять docs/HANDOFF.md по завершении этапа и перед ожидаемым исчерпанием
контекста/перерывом: текущее состояние, решения, изменённые файлы, проверки,
незакрытые замечания, процессы, следующий конкретный шаг. Не писать секреты.
Если граница контекста известна заранее, отправить краткий итог пользователю
до неё. Точного счётчика оставшихся токенов и гарантированного предупреждения
может не быть; поэтому checkpoint делается регулярно, а не только в конце окна.
