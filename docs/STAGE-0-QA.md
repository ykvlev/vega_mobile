# Этап 0 — независимая документарная приёмка QA

> Исторический отчёт этапа 0 по прежним правилам. Актуальные бизнес-решения
> находятся в [DECISIONS.md](DECISIONS.md): цены/наличие после одобрения,
> любые отрезы Color/Color Ultima при ≤2 рулонах запрещены, отдельная админка
> и резерв ожидания оплаты исключены. Этот отчёт не подтверждает новый scope.


Дата: 2026-10-24 (клиентский календарь, Europe/Moscow). Reviewer: QA-направление, отдельно от авторов архитектуры,
мобильного приложения и backend. Основание: scope в STAGE-0.md и строгий gate
QUALITY-PLAN.md.

## Вердикт и границы

**PASS — только согласованность перечисленной ниже спецификации и допуск к
bootstrap.** Это не PASS работающего приложения, тестов, CI, интеграций, деплоя,
подписанных сборок или production-продаж. Исполняемая реализация не принималась.

Git HEAD отсутствует: commit SHA не существует. Вместо выдуманного SHA проверенный
документарный артефакт привязан к SHA-256 нормативных файлов в manifest ниже.
Изменения этих файлов после снимка требуют оценки затронутых критериев и нового
заключения. STAGE-0.md прочитан как scope/status report, но исключён из immutable
manifest: обновление только его статуса после verdict не меняет принятый контракт.

Scope: STAGE-0, DECISIONS, API-CONTRACT, ARCHITECTURE, MOBILE, BACKEND, PAYMENTS
и QUALITY-PLAN. Проверены согласованность правил, транспортных соглашений,
протокола восстановления и границ demo/production, а также локальные ссылки
этих документов. Открытых конкретных противоречий в этом scope не обнаружено.

## Результаты документарных проверок

| Критерий | Результат |
|---|---|
| Две аудитории; гостевой каталог без цен/остатков, закрытые offers после входа | Согласовано; серверные DTO и разделение кэша описаны |
| Вход телефон/пароль, SMS позже; неподтверждённый номер не считается проверенным | Согласовано; рабочие аккаунты ограничены отдельным security gate |
| Длина полного рулона у SKU; при <=2 целых нарезка запрещена, готовый достаточный отрез разрешён | Согласовано; сумма коротких отрезов не заменяет непрерывную длину |
| amountMinor и lengthMm — строки целых минимальных единиц | Согласовано между API, backend, архитектурой и mobile |
| lineId, unique(cartId, skuId, unit), вложенный quantity и optimistic versions | Согласовано; метры и рулоны одного SKU не перезаписывают друг друга |
| Recovery после timeout/restart | Тот же POST/key/payload; in-progress, конфликт и retention/tombstone описаны без нового ключа при неизвестном исходе |
| Quote/submit и 1С | Актуальная проверка до создания рабочего заказа; отказ сохраняет корзину, не маскируется принятой заявкой |
| Менеджерские условия и принятие клиентом | Версии состава/суммы/доставки фиксированы; изменение отзывает прежнее право оплаты |
| Оплата и исполнение | Раздельные состояния; доверенное подтверждение 100%, redirect/скриншот не proof |
| Границы внешних операций | Нет обещания общей ACID с 1С; pending/unknown, идемпотентность, сверка и компенсации заданы |
| Production доступность | Перед оплатой проверка и согласованный резерв 1С; unavailable/stale не разрешают торговлю по snapshot |
| Возвраты | Одинаковый лимит succeeded + pending/unknown + new <= received, без двойного вычитания |
| Строгий QA gate | FAIL/BLOCKED запрещает зависимое продвижение; исправление → независимый retest и регрессия |
| Локальные ссылки scope | Скрипт проверки существования целей: broken = 0 |

## Закрытые замечания текущего review

1. Неоднозначные «десятичные строки» в ARCHITECTURE заменены на точные integer
   minor units/mm согласно API-CONTRACT; исправление перепроверено.
2. Плоское тело количества в BACKEND заменено вложенным quantity; transitions
   используют expectedOrderVersion, stale/unavailable — нормативный код
   INVENTORY_CONFIRMATION_UNAVAILABLE; исправления перепроверены.
3. MOBILE явно требует актуальную 1С для quote/submit до появления заказа,
   а также повторный check/reserve до оплаты; не выдаёт заявку вместо отказа.

Финальная CRITICAL-REVIEW.md перечитана: прежние пункты про lineId, recovery и QA
закрыты документарно и согласованы с независимой перепроверкой выше; новых
документарных блокеров критик не обнаружил. Итог SECURITY.md разрешает bootstrap
на тестовых данных, но явно не выдаёт security sign-off рабочего релиза.
Эти review не закрывают будущие runtime-тесты.

## Что остаётся заблокированным

Production: проверенные 1С и общий резерв, платёжный провайдер/merchant account,
фискальная схема где применимо, безопасная верификация/recovery аккаунтов,
TTL/retention, шаг/минимум и коммерческая конфигурация, подтверждённые доставка
и суммы конкретного заказа, обязательные sandbox/live signoff и сквозные тесты.

Runtime и CI ещё не проверены. Следующий gate требует чистой установки,
миграций и PostgreSQL, содержательных тестов, сборок и реальных CI checks;
GitHub enforcement признаётся только после настройки и проверки. Допускается
bootstrap с именованными dev fixtures и изолированными fake adapters, без
реальных денег, клиентов и автоматического demo fallback рабочего режима.
