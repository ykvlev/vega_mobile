# Этап 0: согласованная основа

> Исторический отчёт этапа 0 по прежним правилам. Актуальные бизнес-решения
> находятся в [DECISIONS.md](DECISIONS.md): цены/наличие после одобрения,
> любые отрезы Color/Color Ultima при ≤2 рулонах запрещены, отдельная админка
> и резерв ожидания оплаты исключены. Этот отчёт не подтверждает новый scope.


Scope: спецификации, контракты и готовность начать bootstrap. Не включает
работающие приложения, реальные интеграции, CI runners и production sign-off.
Статус: PASS документарной готовности к bootstrap. Независимые QA и критик
завершили review, замечания исправлены и перепроверены. Подробности и SHA-256
принятых файлов — STAGE-0-QA.md; это не runtime/CI/production PASS.

## Подтверждённые пользовательские требования

| Область | Принятое правило |
|---|---|
| Аудитория | Автовладельцы и студии; автомобиль, каталог, быстрый поиск на главной |
| Визуал | Тёмный pushr по просмотренным скриншотам; точные шрифты/анимации неизвестны |
| Гость | Каталог без цен и остатков; серверное исключение полей, приватный кэш отдельно |
| Вход | Телефон+пароль сначала; SMS позже |
| Единицы | Метры/полные рулоны; длина полного рулона задана у продаваемого SKU |
| Остатки | При <=2 целых не режем целые, но продаём существующие достаточные отрезы |
| 1С | Источник доступности; отсутствие SKU/остатка запрещает рабочий заказ |
| Заказ | Клиент подаёт → менеджер согласует → клиент принимает условия |
| Оплата | Обязательная онлайн-оплата, также счёт юрлиц; 100% до отправки |
| Доставка | Менеджер согласует сумму и порядок до оплаты; перевозчики в DECISIONS.md |

## Технические решения для первой реализации

- Модульный API, PostgreSQL, отдельные mobile/admin; предложенный стек в ARCHITECTURE.md.
- Отдельный cart lineId и уникальность (cartId, skuId, unit); одна плёнка метрами
  и рулонами не перезаписывает соседнюю позицию.
- Recovery мутации: сохранить операцию и ключ, повторить тот же POST/payload/key.
  Не искать созданный заказ эвристикой по списку и не заводить новый ключ при timeout.
- Отдельные состояния order/payment/reservation. Менеджерская версия условий
  неизменна; изменение состава/суммы/доставки требует нового принятия.
- Внешние вызовы 1С/провайдера вне долгой SQL-транзакции; явные pending/unknown,
  сверка, идемпотентность, outbox. Не обещать общую ACID-транзакцию с 1С.
- Недоступная production 1С не заменяется автоматически демонстрационным адаптером.
- До рабочего подтверждения владения номером можно использовать только изолированные
  dev-профили. Само введение номера не означает проверенного владельца.
- Начальные dev fixture параметры не считать подтверждёнными коммерческими условиями.
  Неуказанные обязательные параметры production вызывают ошибку readiness для торговли.

## Сценарии для последующих исполняемых тестов

Это ожидаемые результаты, а не отчёт о выполненных тестах.

1. Один SKU: добавить рулон и метры, изменить/удалить одну строку — другая сохранена.
2. 3 целых рулона: нарезка разрешена лишь при достаточном допустимом источнике.
3. 2/1/0 целых: новая нарезка из целых запрещена; достаточный готовый отрез доступен.
4. Два коротких отреза с достаточной суммой не считаются одним непрерывным.
5. Сервер создал заказ, ответ потерян, клиент перезапущен — replay возвращает тот же
   заказ, без второго заказа/резерва; другой payload с тем же ключом — конфликт.
6. SKU отсутствует в 1С или мало остатка — рабочий submit запрещён; устаревшая
   проверка/неизвестный резерв также не дают перейти к оплате.
7. Менеджер ещё не согласовал заказ — платёж создать нельзя. Новая версия условий
   отменяет право платить по старым условиям после безопасной сверки активной попытки.
8. Фальшивый redirect не меняет paid; повтор webhook не дублирует списание/исполнение.
9. Счёт/карта без подтверждённых 100% не разрешают отправку; скриншот не proof.
10. Гость не получает цены/остатки в API, поиске, фильтрах и публичном кэше.
